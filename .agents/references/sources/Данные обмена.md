## Назначение

- Отвечает, что остаётся в базе после обмена и по каким ключам это связано.
- На выходе — понимание, где искать след сообщения и какие поля нельзя читать.
- **Не:**
	- Описывает порядок вызовов: это `docs/TRFTS/Поток обмена.md`.
	- Заменяет DDL. Перечислены только поля, назначение которых из имени не следует.

## Сущности

| Сущность | Гранулярность | Смысл |
| --- | --- | --- |
| `TR_FTSExchangeCfg` | Участник мониторинга | Настройка стороны обмена |
| `TR_FTSExchange` | Цепочка | Группа связанных сообщений |
| `TR_FTSExchangeHistory` | Сообщение | Одно отправленное или принятое сообщение |
| `TR_FTSRequest` | HTTP-вызов | Сырой запрос и ответ |
| `TR_FTSExchangeDocLink` | Связь | Документ, привязанный к сообщению |
| `BTS_ExchangeFunction` | Метод | Функция обмена, сквозной ключ модуля |
| `BTS_ExchangeFunctionVer` | Пара | Версия API на функцию и конфигурацию |

Связи: конфигурация содержит цепочки, цепочка содержит сообщения, сообщение ссылается на HTTP-вызов и на привязанные документы.

Направление вызова хранится в `TR_FTSRequest` первым аргументом создания: `1` входящий, `-1` исходящий.

## Цепочка

- Ключ цепочки — `TR_FTSExchange.sGroup`. В него кладётся `TicketId` инициирующего запроса.
- Входящее сообщение попадает в цепочку по `TicketId` из тела. Исходящее наследует группу от родительского обмена.
- `TicketId` исходящего файла собственный, не копия. Копирование требуется только для синхронного `ServiceResponse`, и только там ФНС это оговаривает.
- Следствие: связать входящее сообщение ФНС с нашим предыдущим по `TicketId` нельзя. Связь строится по предметному идентификатору из тела.
- `idParent` заполняется только там, где нужен порядок сообщений. Для остальных случаев хватает группы и даты.

## Документы и подписи

- Привязка документа к сообщению — `TR_FTSExchangeDocLink`. Тип связи задаёт роль документа в сообщении.
- Порядковый номер пункта, если он нужен сценарию, лежит в связи, а не в документе.
- `HandleBeforeOut` копирует привязки документов от родительского сообщения. Копирование не проверяет дубли: повторный вызов с тем же родителем удваивает связи.
- Подпись живёт в `BTK_SignDoc` и ссылается на версию файла, не на документ.
- Признак `bFNSSend` отделяет подпись для передачи в налоговый орган от подписей обмена с контрагентами. Такая подпись на версии одна: при добавлении новой прежняя удаляется.
- Подпись читает только служебный метод скачивания. В момент сборки исходящего файла она не нужна, но обязана существовать до прихода ФНС по ссылке.

## Настройка

| Где | Что задаёт |
| --- | --- |
| `TR_FTSExchangeCfg.sSelfURL` | Домен наших сервисов, попадает в ссылки для ФНС |
| `TR_FTSExchangeCfg.sThirdPartyURL` | Домен сервисов ФНС |
| `TR_FTSExchangeCfg.sToken` | Токен аутентификации, живёт 24 часа |
| `TR_FTSExchangeCfg.idSelfContras` | Участник мониторинга, его ИНН сверяется с входящим |
| `TR_FTSExchangeCfg.nOrder` | Конфигурация по умолчанию: `1` |
| `TR_FTSExchangeCfg.bAvailable` | Участие в массовых заданиях |
| `BTS_ExchangeFunction.sUrlPath` | Путь метода в адресе |
| `BTS_ExchangeFunction.sOracleFunction` | Имя функции реализации без пакета |
| `BTS_ExchangeFunction.sXMLNSAttrSubDomen` | Хвост namespace схемы, вместе с версией схемы |
| `BTS_ExchangeFunction.bActive` | Приём метода |
| `BTS_ExchangeFunctionVer.idFTSAPIVersion` | Версия API на пару «функция и конфигурация» |

- Настройки версии нет — сборка адреса возбуждает ошибку. Умолчания нет намеренно.
- Уникальность версии на пару в базе не обеспечена. Дубль гасится выбором максимума.

## Пробелы

- DDL таблиц модуля в репозитории нет. Состав колонок восстановлен по обращениям из кода, полнота не гарантирована.
- Читается ли `TR_FTSExchangeHistory.idFTSDocLinkType` вне репозитория — из клиента, представлений, отчётов — проверить нечем.
- Версия применённого обмена в истории не хранится. По факту обмена восстановить, в какой версии он прошёл, нельзя.
