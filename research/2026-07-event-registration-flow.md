# Флоу регистрации на этапы мероприятия (EP-1)

Контекст: регистрация идёт на **этапы** (EventStage), не на мероприятие целиком. MVP собирает ~0 доп-полей на этап; в будущем — пошаговый мастер с опросником/оплатой на этап и общей суммой в конце. Приоритет владельца — минимум кликов и удержание контекста при большом числе этапов (GDPS, `.../docs/product/users-and-roles.md` и `.../docs/product/domain-model.md` §3).

## Findings

- **[high] Порог «одна страница vs мастер» задаётся объёмом данных.** Короткая/бесплатная регистрация (RSVP, ≤5 полей) — одностраничная форма: быстрее, прозрачнее, меньше отказов. Мастер оправдан при 6+ полях, нескольких типах билетов, доп-опциях и оплате. (источники: Zuko, Designlab, Eleken)
- **[high] Оптимум мастера — 2–4 шага.** Дальше растёт усталость, если данные не по-настоящему сложные. Обязательны: прогресс-бар с **подписанными** шагами (не процент) и навигация назад **без потери введённого**. (источники: Eleken, Lollypop, Designlab)
- **[high] Индустриальный паттерн для мультисессионных мероприятий един:** на странице — список сессий/этапов с **чекбоксами**, выбранные складываются в «корзину», далее единый **checkout** (подтверждение + оплата, если платно). Так устроены Eventzilla, Blackthorn, SugarCRM Market. (источники ниже)
- **[moderate] Конфиг сессии у этих платформ включает и число мест, и цену на конкретную сессию** — ровно то, что владелец назвал «на будущее» (лимит мест и оплата на уровне этапа). Значит наша модель «регистрация = первоклассная сущность у этапа со статусом» совпадает с проверенным подходом. (источники: Eventzilla, Blackthorn)
- **[moderate] «Выбор → checkout» — это уже мастер, просто с одним шагом.** MVP-экран «отметил этапы галочками → кнопка Регистрация» буквально является шагом 1 будущего мастера `выбор → [данные/оплата по этапу] → сводка/оплата`. Достройка = вставка промежуточных шагов, а не переделка. (вывод из паттерна выше)

## Hypotheses

- **H1: MVP не нужен мастер — достаточно одной страницы.** MVP собирает ~0 доп-полей на этап → по правилу «≤5 полей = одна страница» мастер избыточен. — *подтверждается* (Zuko/Designlab: мастер вводят только когда появляются данные/оплата).
- **H2: Модель «выбор этапов (клиентский массив) → confirm» расширяется аддитивно.** Если состояние выбора хранить как список выбранных этапов на клиенте, вставка шагов (опросник/оплата на этап, финальная сводка) не ломает MVP-разметку. — *подтверждается* индустриальным паттерном cart→checkout.

## Conclusion

**MVP EP-1 — одностраничный выбор этапов, являющийся шагом 1 будущего мастера.** На странице мероприятия у каждого этапа, на который можно регистрироваться (есть `dRegistrationEndDate` в будущем), — чекбокс; внизу общая кнопка «Регистрация», неактивная пока ничего не выбрано; по клику — confirm и запись регистраций на выбранные этапы. Мёртвую верхнюю кнопку демонтировать.

Расширяемость без переделки:
- Состояние выбора — **список выбранных этапов на клиенте** (массив), а не одиночный флаг. Вставка будущих шагов (`выбор → [опросник/оплата по этапу] → сводка/оплата`) становится аддитивной — подтверждённый индустриальный паттерн cart→checkout (2–4 шага, подписанный прогресс, назад без потери данных).
- Регистрация — **первоклассная сущность у этапа со своим статусом** (Person↔EventStage rel + справочник статусов), под которую позже встают оплата/билет (цена, дата покупки/оплаты), лимит мест, заявка-с-подтверждением, список участников с согласием. Совпадает с конфигом сессий у Eventzilla/Blackthorn (места + цена на сессию).

Отложено (не EP-1, всплывёт при достройке): роут vs модалка для шага на этап; отображение разных типов участия (регистрация/волонтёр/партнёр) без перегруза меню.

→ Питает `plan-new` EP-1.
