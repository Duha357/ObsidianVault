## Выводы

- Резолюцию для пользователя пишут как заметку о выпуске: что пользователь теперь может или видит иначе, а не что поменяли в коде [moderate] — Keep a Changelog, GitLab Changelog entries, Lynch «Refactoring English», HFLabs (Habr), Kubernetes Release Notes.
- Рабочая форма — 2 слоя: 1–3 фразы для пользователя плюс ссылка на технический слой (МР, дока, отчёт) [moderate] — Kubernetes, GitLab, HFLabs, ServiceNow/Zendesk public vs work notes, Gwinnett County KB.
- Ярлык резолюции без пояснения читается как отказ без причины. Каждому типу нужна своя обязательная деталь [moderate] — Django Triaging tickets, Mozilla BMO, Microsoft VS Problem Status, KDE bug 383753, Help Scout.
- Duplicate — ссылка на основную задачу, только при той же самой проблеме [high] — Django, Mozilla BMO, Microsoft Connect, ZenTao API.
- Works as designed / Rejected — основание решения и обходной путь или куда идти при несогласии [moderate] — Django wontfix, Micahel (MS), Help Scout.
- Низкая важность — «не сейчас» и условие пересмотра [low] — Microsoft VS «Lower Priority», Herath «On WontFixing Bugs».
- Подсказка «представь пользователя» сама по себе не снимает проклятие знания. Работает опора на реальные слова читателя и чтение черновика другим человеком [moderate] — Eyal/Steffel/Epley 2018, Damen et al. 2020, Hinds 1999, Pinker 2014–2015, Keysar & Henly 2002.
- Узкий вопрос — один предмет, понятно, что считать ответом. Широкий вопрос даёт отписку [moderate] — Dillman (конспект UC Davis), Tourangeau et al. 2000.
- Шпаргалка держится в голове при 4±1 пункте [moderate] — Cowan 2001. Длина «5–9 пунктов» прослежена только до Gawande [low].
- Обязательное поле или чек-лист без смысла заполняют формально. Нужны пример и выборочная проверка [low] — Urbach NEJM 2014, 黄维健 2026, THWACK, hivel.ai, Moveworks.
- Называть результат, а не действие [moderate] — Degani & Wiener NASA 1994 («six thousand for seven thousand»), BLUF AR 25-50, пирамида Минто, Lynch.
- Текст для пользователя пишут в момент сдачи работы, а не потом [low] — Kubernetes (release-note блокирует мерж, вариант NONE), GitLab, Amazon Working Backwards.

## Спорное

- Резолюция для пользователя против резолюции для следующего инженера (Giva, Moveworks, KCS: в fix — точные изменения) — расхождение снимается 2 слоями.
- «Release notes никто не читает» против «читают» — HN-тред без данных; вендорские цифры 67% против 83,2% с конфликтом интересов. На вывод не влияет: резолюцию читает конкретный автор задачи.
- Переименование ярлыков снимает обиду (KDE) против «любое закрытие без фикса воспринимается плохо» (Feck, там же) — у нас ярлыки фиксированы, решает текст.

## Пробелы

- Прямых исследований эффекта правил на качество close notes не найдено.
- Готовых формулировок для «Работает как задумано», «Потеряна актуальность», «Незначительная важность» нет нигде — выведены по аналогии с wontfix/Lower Priority.
- RU-источников про комментарий к закрытию задачи нет, кроме HFLabs (release notes) и документации Яндекс Трекера.
- ZH-источники описывают только список резолюций (ZenTao, Huawei CodeArts), не формулировки.
- Первоисточник ITIL (PeopleCert) не открыт.
- Внутренние правила оформления заказчика («наши правила») в исследование не переданы.

## Практические выводы

- Каркас: «было → стало» для пользователя, «что ему делать», «где детали».
- Мелкая задача — 1 предложение. Крупная — 3–5 строк и ссылки, детали за ссылкой.
- Вопросы — узкие, с опорой на текст задачи, 4±1 штука плюс 1 строка на тип.
- Проверка крупной резолюции — прочитать автору задачи или коллеге из другой команды, не себе.
- Разбор примеров пользователя:
	- Фильтр («IS DISTINCT FROM, SQL и JEXL») — механизм вместо эффекта. Эффект: «записи с пустым полем больше не пропадают из фильтров „не равно“ и т.д.». Техника — в МР.
	- Скрытие стеков — нет границы: весь прикладной код или только часть.
	- HtmlFrame — нет действия для читателя: прикладникам следовать доке по ссылке.
	- Нагрузочные тесты — нет вывода и цифр; ссылки на МР и репо есть.

## Противоречия

| Тезис А | Источник А | Тезис Б | Источник Б | Характер | Как разрешается |
|---|---|---|---|---|---|
| В fix писать точные технические изменения | Giva, Moveworks, KCS | Писать эффект для пользователя, технику убрать | Keep a Changelog, GitLab, HFLabs | Разные индустрии (ITSM-база знаний против продуктовых заметок) | 2 слоя: текст для пользователя + ссылка на МР |
| Дебиасинг через «представь читателя» работает | популярные гайды (Лайфхакер, Habr) | Не работает, иногда ухудшает | Eyal 2018, Damen 2020, Hinds 1999 | Наука против практики | Вопросы к реальному тексту задачи + чтение другим |
| Чек-листы улучшают исходы | Gawande (пересказ), SBAR-обзоры | Внедрение без смысла не меняет исходы | Urbach 2014, 黄维健 2026 | Разные условия внедрения | Короткий список + пример + выборочная проверка |

## Оценка гипотез

| Свидетельство (вес) | H1 каркас + узкие вопросы | H2 только шаблон-поля | H3 два слоя | H0 гайды не работают, только ревью |
|---|---|---|---|---|
| Release-notes-гайды: эффект, не механизм (8) | C | нейтр. | C | нейтр. |
| Обязательные поля → мусор (4–5) | нейтр. | N | нейтр. | C |
| Kubernetes/GitLab: заметка в PR работает (9) | C | C | C | N |
| Eyal/Damen/Hinds: представлять читателя бесполезно (8–9) | C при вопросах к тексту задачи | нейтр. | нейтр. | C |
| Urbach: формальный чек-лист без эффекта (8) | N при длинном списке | N | нейтр. | C |
| Dillman/Tourangeau: узкие вопросы точнее (7–8) | C | N | нейтр. | нейтр. |
| Скрин заказчика: лид возвращает резолюции (контекст) | C | нейтр. | C | C |

- Сильнейшая — H1 + H3 с элементом H0: каркас из 3 слотов, узкие вопросы по типу, ссылка на технику, выборочное ревью.
- Точка хрупкости: нет прямых данных, что узкие вопросы снижают число отписок именно в резолюциях. Опора — исследования опросов и чек-листов.
