# Архитектура знаний проекта для Claude Code: исследование и проектирование

**Дата:** 04.07.2026. Актуальность рекомендаций — квартал (сам Claude Code меняется еженедельно, см. «What's New» в доках).
**Входные материалы:** промпт-задание, документ new_15 (ПБТ-27 «Использование AI в разработке», 05.05.2026), официальная документация Claude Code (снимок карты доков от 03.06.2026), внешние источники (список в конце).

---

## 0. Резюме (TL;DR)

1. **Главный сдвиг 2026 года, который обесценивает часть вашего исходного плана:** Claude Code больше не «CLAUDE.md + всё остальное». Появились и задокументированы: `.claude/rules/` с path-скоупингом, **auto memory** (Claude сам ведёт `MEMORY.md` per-repo), унификация slash-команд и скиллов, `paths:`-frontmatter у скиллов, `claudeMdExcludes`, `/init` с интерактивным аудитом. Архитектуру надо строить вокруг **четырёх слоёв загрузки** (всегда / по пути / по задаче / по событию), а не вокруг папок.
2. **CLAUDE.md — навигатор, не хранилище.** Официальная норма: <200 строк; раздутый файл заставляет Claude игнорировать инструкции (прямая формулировка Anthropic). Роль: карта проекта + указатели «где что лежит» + 10–20 правил, которые нельзя вывести из кода.
3. **Планы — главный носитель знаний между сессиями.** Консенсус официальных доков, FIC (HumanLayer), Spec Kit и вашего new_15: артефакты research → plan → implementation, лежащие в git, важнее любой «памяти». Рекомендуемое место — `docs/plans/` со статусной моделью и индексом.
4. **Механизм «активного плана»** решается одним файлом-указателем `docs/CURRENT.md` (≤30 строк: что активно, что заморожено, что игнорировать), на который ссылается CLAUDE.md. Это единственная точка, которую вы меняете фразой «работаем по плану B».
5. **Решения** — два журнала: ADR (`docs/decisions/adr/`, технические) и PDR (`docs/decisions/product/`, продуктовые, включая «постоянные запреты» типа «маркетплейса не будет»). Постоянные запреты дублируются одной строкой в CLAUDE.md со ссылкой на PDR.
6. **Исследования** — `docs/research/` с форматом «findings + confidence + open questions + hypotheses» (совпадает с вашим скиллом researcher), один файл на тему, живёт неделями.
7. **Из new_15 брать:** проектные скиллы в репо, `docs/plans/` как память проекта, кросс-ревью второй моделью, verification-before-completion, worktree для долгих циклов, hooks для принудительных проверок. **Не брать буквально:** тезис «CLAUDE.md почти не нужен» (доки 2026 его опровергают — файл нужен, но короткий и навигационный) и перенос корпоративной инфраструктуры (Глория/RAG, X11, JDWP) на соло-проект — избыточно на этом этапе.

## 1. Методология

Режим — глубокий (высокие ставки: архитектура на месяцы). Классы источников: официальная документация (вес 9), методологии с проверяемыми кейсами (FIC/HumanLayer — 35k LOC PR в BAML; Spec Kit — вес 7), практические разборы и негативные кейсы (вес 4–6), внутренний документ new_15 (вес 6: практик, но одна точка зрения, серая литература). Оппозиционные запросы закрыты: раздувание CLAUDE.md, нетриггерящиеся скиллы (эвал Vercel: скиллы не вызвались в 56% тестов), гниение доков, проблемы spec-driven в brownfield. Насыщение достигнуто: последние итерации поиска повторяли уже найденные тезисы.

Маркировка утверждений по тексту:
- **[Д]** — документированное поведение Claude Code (официальные доки, снимок 06.2026);
- **[В]** — выведенное/наблюдаемое поведение (не гарантировано, может измениться);
- **[П]** — лучшая практика сообщества (подтверждена ≥2 независимыми источниками);
- **[Р]** — моя рекомендация под ваш проект.

Уверенность: **high / moderate / low** по GRADE-подобной шкале.

## 2. Часть A. Как Claude Code реально работает с документацией репозитория

### 2.1. Слои контекста и когда они загружаются [Д, high]

| Механизм | Когда загружается | Что загружается | Цена контекста |
|---|---|---|---|
| CLAUDE.md (managed → user → project → local) | Старт сессии, полностью | Весь текст, включая `@`-импорты | Каждый запрос |
| CLAUDE.md в поддиректориях | По требованию — когда Claude читает файлы там | Весь файл | По факту использования |
| `.claude/rules/*.md` без `paths:` | Старт сессии | Весь файл | Каждый запрос |
| `.claude/rules/*.md` с `paths:` | Когда Claude читает файл под глоб | Весь файл | По факту |
| Скиллы (`.claude/skills/*/SKILL.md`) | Описания — на старте; полный текст — при вызове `/<name>` или когда Claude сам решил, что релевантно; `paths:`-frontmatter грузит скилл при работе с совпадающими файлами | name+description всегда; тело — по требованию | Низкая до вызова |
| Скиллы с `disable-model-invocation: true` | Только ручной вызов | Ничего до вызова | Ноль |
| Auto memory (`~/.claude/projects/<repo>/memory/MEMORY.md`) | Старт сессии: первые 200 строк или 25KB | Индекс; тематические файлы (`debugging.md` и т.п.) Claude читает сам по мере надобности | Умеренная |
| MCP | Старт: имена тулов; схемы — при использовании (tool search включён по умолчанию) | Минимум до вызова | Низкая |
| Hooks | Никогда (исполняются снаружи), кроме возвращаемого вывода | stdout хука попадает в контекст | Ноль/по факту |
| Subagents | При спавне: свежий контекст + CLAUDE.md + скиллы из поля `skills:` (предзагружаются целиком) | Изолировано от основной сессии | Изолировано |

Ключевые детали [Д, high]:
- **Порядок конкатенации CLAUDE.md:** от корня ФС вниз к рабочей директории; ближние к точке запуска читаются последними; `CLAUDE.local.md` — после `CLAUDE.md` на том же уровне. Файлы не перекрывают, а складываются; при конфликте Claude выбирает произвольно → конфликтующие правила надо чистить.
- **`@`-импорты**: разворачиваются на старте (глубина до 4), **не экономят контекст** — только организуют. Путь в бэктиках не импортируется. Первый внешний импорт — диалог одобрения.
- **HTML-комментарии** (`<!-- -->`) в CLAUDE.md вырезаются перед подачей в контекст — легальное место для заметок мейнтейнеру.
- **AGENTS.md Claude Code не читает.** Паттерн для мультиагентности: `CLAUDE.md` = `@AGENTS.md` + Claude-специфичные добавки, либо симлинк (на Windows — только импорт).
- **Компакция:** корневой CLAUDE.md перечитывается с диска и ре-инжектится после `/compact`; вложенные — нет (перезагрузятся при следующем чтении файлов там). Инструкции «только из разговора» теряются → всё важное должно жить в файлах.
- **Precedence при коллизии имён:** скиллы — managed > user > project; субагенты — managed > CLI > project > user > plugin; MCP — local > project > user. CLAUDE.md — аддитивен. Hooks — все срабатывают.
- **`/memory`** показывает, какие файлы инструкций реально загружены; хук `InstructionsLoaded` логирует загрузку — главный инструмент отладки «почему Claude не видит мой док».
- **CLAUDE.md — user-message после системного промпта, не системный промпт** → это контекст, а не enforcement. Всё, что обязано выполняться всегда, — в hooks (`PreToolUse` блокирует, `Stop` не даёт завершиться без проверки) или в `permissions.deny`.
- **Slash-команды и скиллы унифицированы**: `.claude/commands/*.md` продолжает работать, но концептуально команда = скилл с ручным вызовом; `$ARGUMENTS` поддерживается в скиллах. [Д, moderate — терминология активно меняется]
- **Settings** (`.claude/settings.json`) загружаются **только из директории запуска**, не наследуются вверх, в отличие от CLAUDE.md. Для монорепо это значит: настройки должны быть самодостаточны в каждой точке входа.
- **Auto memory** (v2.1.59+): включена по умолчанию, машинно-локальна, общая для всех worktree одного репо. Это память *Claude о вас*, не носитель командного знания — командное знание живёт в git.

### 2.2. Как Claude решает, какой контекст использовать [Д+В, high]

1. На старте в контексте: system prompt → managed/user/project CLAUDE.md + безусловные rules → первые 200 строк MEMORY.md → имена MCP-тулов → name+description всех скиллов.
2. Дальше Claude **сам** выбирает: скилл — по совпадению описания с задачей (описания при большом числе скиллов **обрезаются** → ключевые слова должны быть в начале); rules/вложенные CLAUDE.md — по факту чтения файлов; тематические файлы памяти — по индексу MEMORY.md.
3. Вывод для архитектуры: **дискавери важнее содержания**. Документ, на который нет указателя из CLAUDE.md, описания скилла или индекса, для агента не существует. Практика подтверждает [П, high]: «нельзя быть уверенным на 100%, что агент прочтёт док, когда столкнётся с проблемой» — надёжнее явные указатели («при проблемах с X сначала читай docs/x-gotchas.md») и хуки, чем надежда на автотриггер (Vercel: скиллы не вызывались в 56% кейсов их эвала).

## 3. Часть B. Подходы сообщества: сравнение и противоречия

### 3.1. Четыре школы

**1) Официальная линия Anthropic** [Д]: минимальный CLAUDE.md (<200 строк, «каждая строка должна предотвращать ошибку»), справочный материал — в скиллы, path-специфика — в rules, принуждение — в hooks, план сложной задачи — «сохрани в markdown-файл в репо, он переживёт компакцию», ревью — свежим субагентом («adversarial review»), спека — через «Claude интервьюирует тебя → SPEC.md → новая сессия исполняет».

**2) FIC / Advanced Context Engineering (HumanLayer)** [П, high — проверено на 300k LOC Rust, PR на 35k строк]: цикл **Research → Plan → Implement**, каждая фаза — свежий контекст, вход — компактный артефакт предыдущей фазы. Утилизация контекста 40–60%. Артефакты — в `thoughts/shared/{research,plans}/` с датированными именами (`2025-08-05_baml_test_assertions.md`). Ключевой тезис: **человеческое ревью смещается с кода на план** («ревьюишь 200 строк плана вместо 2000 строк кода»); плохая строка плана каскадирует в сотни плохих строк кода. Честная оговорка авторов: без глубокой вовлечённости человека в research/plan «это НЕ работает».

**3) Spec-Driven Development / GitHub Spec Kit** [П, moderate]: `constitution.md` (неизменяемые принципы проекта) → `/specify` (что и зачем) → `/clarify` → `/plan` (как) → `/tasks` (разбивка с зависимостями и метками параллельности) → `/analyze` (кросс-проверка артефактов на противоречия и нарушения конституции) → `/implement`. Всё в `.specify/`, спека привязана к git-ветке. Полезные идеи: конституция как отдельный класс документов; `/analyze` как гейт консистентности. Известные слабости [П]: тяжело в brownfield; растёт стоимость токенов; открытая проблема «мастер-спека vs дельта-спеки» (обсуждение #152 в репо не решено — со временем «что делает система» размазывается по десяткам фиче-спек).

**4) Superpowers-экосистема / ваш new_15** [В+П, moderate]: скиллы — главный носитель workflow-знаний; `docs/plans/` в git — «память проекта, часто полезнее кода»; CLAUDE.md — «короткая шапка»; кросс-модельное ревью; RALPHEX-циклы с progress-журналом (очищается разговорный контекст, но не журнал результатов).

### 3.2. Таблица противоречий и разрешение

| Тезис А | Тезис Б | Разрешение |
|---|---|---|

### 3.3. Консенсус (все четыре школы + доки) [high]

1. Контекст — главный ограниченный ресурс; качество деградирует с заполнением.
2. Знание живёт в файлах в git, а не в истории чата; сессии одноразовы.
3. Планирование отделено от исполнения; план — ревьюируемый артефакт.
4. Верификация встроена в цикл (тесты/сборка/скриншоты/Stop-hook); «looks done» ≠ done.
5. Ревью — свежим контекстом (субагент/другая модель/новая сессия).
6. Документы для агента пишутся иначе, чем для людей: короче, конкретнее, проверяемо, с ключевыми словами для дискавери.

## 4. Часть C. Рекомендуемая архитектура документации (для GDPS)

### 4.1. Принципы [Р]

- **П1. Слой загрузки определяется частотой нужности**, а не типом документа: всегда → CLAUDE.md/rules; при работе с областью → path-rules / вложенный CLAUDE.md / `paths:`-скилл; при типе задачи → скилл; по событию → hook; по явной ссылке → docs/*.
- **П2. Один вопрос — один авторитетный документ.** Дубли запрещены; вместо копии — ссылка. (Это же правило у вас уже работает в онтологии КамаДев.)
- **П3. Каждый док имеет фронтматтер:** `status`, `updated`, `owner` (вы/Claude/оба). Стейл-док вреднее отсутствующего [П].
- **П4. Дискавери обязателен:** всё, что должен находить агент, достижимо ≤2 переходами из CLAUDE.md (CLAUDE.md → индекс раздела → документ).
- **П5. Принуждение ≠ инструкция.** «Не трогать роуты» — это hook/permissions.deny, а не строчка в CLAUDE.md (строчка тоже есть, но как объяснение, почему хук вас заблокировал).
- **П6. Монорепо-совместимость:** структура кладётся в корень будущего монорепо; для пакетов — вложенные CLAUDE.md по официальному паттерну large-codebases.

### 4.2. Дерево репозитория [Р]

## 5. Часть D. Иерархия планирования [Р, П]

Пять уровней достаточно; больше — бюрократия для соло-проекта:

```
Vision (годы, docs/product/vision.md)
  └─ Scope MVP/v1 (docs/product/scope.md)
      └─ Roadmap: эпики EP-N (docs/roadmap.md; статусы: idea/next/active/done/cancelled)
          └─ Планы PLAN-* (docs/plans/; фича/эксперимент/миграция/техдолг — один формат)
              └─ Шаги-чекбоксы внутри плана (+ TaskCreate/TodoWrite в сессии — эфемерно)
```

Правила связывания:
- Каждый план ссылается на эпик (`epic: EP-3`); «Продолжи EP-3» = найти в roadmap эпик → его активные планы → их Progress log.
- **Техдолг — это эпики/планы того же формата** с тегом `kind: tech-debt` в roadmap, конкурирующие за приоритет с фичами в одном списке. Отдельный «tech-debt.md» плодит второй бэклог, который никто не читает [П, moderate].
- **Cancelled — раздел roadmap + архив планов с полем `cancelled-reason`.** Отменённое — самое ценное анти-знание: без него агент (и вы через полгода) предложит то же самое снова [П, high — та же логика, что rejected-ADR].
- Идеи/бэклог — секция `## Icebox` в roadmap.md, одна строка на идею. Отдельная система не нужна, пока строк <50.
- Migration/design-планы — обычные PLAN-* (`kind: migration`); формат один, различие в метаданных. Меньше форматов = выше дисциплина.

## 7. Часть F. Продуктовое и техническое знание

**Продукт** — 5 файлов из дерева (vision, users-and-roles, domain-model, scope, terminology). Не заводите faq.md/business-rules.md/constraints.md как отдельные сущности на старте: правила сущностей — внутрь domain-model (у каждой сущности секция «Инварианты»), ограничения — в scope («Не-цели») и PDR. Меньше файлов — меньше стейла [Р].

**domain-model.md** — главный продуктовый док для вашего портала. На сущность (Person, Organization, Event, Tag, Bot, Files, Admin): назначение · поля-владельцы (user-editable vs admin-only) · статусы и жизненный цикл (для Event — черновик→модерация→опубликовано→архив, EventStage) · права по ролям · ссылки на релевантные ADR/PDR · «Эволюция» (что известно о будущем, напр. «теги в редизайне — см. PLAN-…»). Bot: секция с ответственностями, поддерживаемыми платформами (Telegram сейчас, Discord — icebox), связью с BotSetting в БД; конфигурация — в architecture/stack.md.

**Техника**: architecture/overview.md (как устроено) + stack.md (на чём) + conventions.md (как пишем — длинная версия; короткая — в rules) + nfr.md. NFR — таблицей: категория | целевой уровень | как проверяем | статус. Проверяемые NFR (perf-бюджет, a11y) сразу подключайте к gdps-verify — NFR без автопроверки гниёт первым [П, moderate].

**Дизайн** [Р, moderate]: `docs/design/design-system.md` (токены, соответствие компонент↔код, статус: designed/implemented/drift) + exports/ c парами `screen.png` + `screen.md` (аннотации: интерактив, состояния, что не видно на статике). ## 8. Часть G. Управление решениями

- **ADR** (docs/decisions/adr/): нумерация 0001-…, формат Nygard/MADR: Status / Context / Decision / Alternatives / Consequences; README-индекс таблицей. Immutable: изменение = новый ADR со `supersedes: 0007`. Триггеры записи — выбор между альтернативами (фреймворк, схема, протокол), «мы решили, что…».
- **PDR** (docs/decisions/product/): тот же формат, продуктовые решения. **Постоянные запреты** («маркетплейса не будет», «роуты не менять», «теги переезжают на новую схему») формализуются трёхслойно [Р, high]:
	1. PDR с контекстом и причиной (полное знание);
	2. одна строка в CLAUDE.md со ссылкой (всегда в контексте);
	3. если запрет проверяем механически — hook/deny (`permissions.deny: ["Edit(apps/api/src/routes/**)"]` для роутов). Инструкция — просьба, хук — гарантия [Д].
- **Как Claude использует**: CLAUDE.md велит сверяться с индексом ADR перед архитектурным выбором; скилл /adr-new ловит моменты решения («записать это решение?») и пишет черновик только после вашего подтверждения; reviewer-агент проверяет дифф на противоречие принятым ADR. Важно [П]: авто-сгенерированные из скана кодовой базы ADR фиксируют «что», но выдумывают «почему» — Context всегда ревьюйте.
- Отклонённые идеи — ADR/PDR со статусом `rejected`: дешёвая страховка от повторных дебатов с самим собой и с агентом.

## 12. Часть K. Антипаттерны и типичные ошибки

1. **Раздутый CLAUDE.md** — официально задокументированный отказ: «bloated CLAUDE.md files cause Claude to ignore your actual instructions». Порог ~200 строк; тест каждой строки: «уберу — появятся ли ошибки?».
2. **Импорты как «экономия»** — `@`-импорты грузятся на старте целиком; экономит только paths-скоупинг (rules, скиллы) [Д].
3. **Знание только в чате** — умирает при /clear и частично при компакции (вложенные CLAUDE.md не ре-инжектятся) [Д].
4. **Дублирование правды** (правило и в CLAUDE.md, и в rules, и в скилле) → конфликт → произвольный выбор моделью [Д]. Одно место + ссылки.
5. **Надежда на автотриггер скилла для критичного знания** — до 56% не-вызовов в чужих эвалах [П]. Критичное — через явные указатели и hooks.
6. **Инструкция вместо принуждения** («никогда не редактируй роуты» текстом) — просьба, не гарантия [Д]. PreToolUse/deny.
7. **Стейл-документация** — «неверная инструкция хуже отсутствующей» [П]. Лечится фронтматтером updated + /docs-audit + правкой доков в том же PR, что и код.
8. **Второй бэклог** (отдельные tech-debt.md, ideas.md, faq.md...) — размножение мест, которые никто не обновляет. Минимум сущностей.
9. **Кухонная раковина-сессия и правки поверх правок** — официальные failure patterns: /clear между задачами; после двух неудачных коррекций — новая сессия с лучшим промптом.
10. **Линтерные правила в доках агента** («2 пробела») — работа Prettier/ESLint+hook, не контекста [П].
11. **Спека на каждую фичу без долгоживущей модели системы** — фрагментация правды (грабли Spec Kit) [П]. Долгоживущее — domain-model/architecture; короткоживущее — планы.
12. **Автогенерённые ADR без ревью Context** — фиксируют «что», выдумывают «почему» [П].

## 13. Часть L. Конвенции именования [Р]

- Планы: `docs/plans/<yyyy-mm>-<kebab-topic>.md`, id `PLAN-<yyyy-mm>-<topic>`; исследования: `docs/research/<yyyy-mm>-<topic>.md`.
- ADR: `NNNN-<kebab-decision>.md` (0001-…); PDR: `PNNN-…`. Эпики: `EP-N` в roadmap.md.
- Статусы — единый словарь везде: `draft / active / paused / done / cancelled` (+ `accepted / rejected / superseded` для решений).
- Скиллы: `gdps-*` — проектные исполняемые; `plan-*`, `adr-*`, `research-*`, `docs-*` — работа со знанием. В description первыми словами — то, что скажет пользователь («build», «запусти сборку»...), т.к. описания при избытке скиллов обрезаются [Д].
- Файлы — kebab-case, английский; содержимое — как вам удобнее (у вас RU); фронтматтер-ключи — английский (парсибельность).
- Даты ISO `yyyy-mm-dd` во фронтматтере.

## 14. Часть M. План внедрения (порядок работ)

1. Монорепо-склейка 4 репозиториев → сразу положить скелет: CLAUDE.md(навигатор)+AGENTS.md, docs/{CURRENT.md, plans/README.md, decisions/adr/README.md}, .claude/{settings.json с deny на роуты, rules/code-style.md}.

3. Наполнить минимум продукта: scope.md (MVP/не-цели), domain-model.md (7 сущностей, хотя бы по 10 строк), PDR-P001/P002 (маркетплейс, роуты), vision.md — 1 страница.
4. Скиллы волной 1: gdps-build, gdps-verify, plan-new, plan-close. Волной 2: gdps-debug, adr-new, reviewer-агент. Волной 3: research-log, docs-audit, hooks (lint PostToolUse, verify Stop).
