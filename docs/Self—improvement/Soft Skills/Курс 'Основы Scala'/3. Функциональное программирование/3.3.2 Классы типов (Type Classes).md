Классы типов решают ту же задачу, что и методы-расширения: добавить поведение типу, исходный код которого менять нельзя. Отличие в том, что поведение здесь описывается интерфейсом и подключается компилятором по типу — это ad-hoc полиморфизм, при котором данные и поведение разделены. Ниже: три составные части паттерна, готовые примеры из экосистемы и то, как он записывался в Scala 2.

---

## Проблема ООП-интерфейсов

Чтобы добавить классу интерфейс в стиле ООП, класс наследуют от этого интерфейса. Проблема возникает, когда класс приходит из чужой библиотеки: изменить его объявление нельзя.

Паттерн Type Classes подключает новый интерфейс к типу извне, не трогая его код. Суть в разделении: данные живут в одном месте, поведение — в другом.

Паттерн состоит из трёх частей.

---

## 1. Описание поведения

Сначала объявляется интерфейс — что именно нужно уметь делать с типом.

> [!example]- Пример: Интерфейс поведения
> Трейт параметризован типом `A`: он описывает способность превращать значение любого типа в строку, но пока ни для какого типа не реализован.
>
> Ожидаемый результат: объявлен тип `Show[A]` с единственным методом `show`.
>
> ```scala
> trait Show[A]:
>   def show(a: A): String
> ```
>
> Пример показывает: зачем поведение выносят в отдельный трейт — оно перестаёт быть частью самого типа данных.

---

## 2. Реализация для конкретного типа

Затем объявляется правило для нужного типа. Ключевое слово `given` делает реализацию доступной компилятору для автоматического поиска (раздел 1.4.5).

> [!example]- Пример: Реализация для Int
> Реализация объявлена отдельно от типа `Int` и находится компилятором по типу, а не по имени.
>
> Ожидаемый результат: для `Int` теперь существует реализация `Show`; для типов без такой реализации использование не скомпилируется.
>
> ```scala
> given Show[Int] with
>   def show(a: Int): String = a.toString
> ```
>
> Пример показывает: для чего нужен `given` — реализация подключается к типу без изменения его объявления.

---

## 3. Синтаксис использования

Чтобы вызывать поведение через точку, добавляется метод-расширение (раздел 3.3.1).

> [!example]- Пример: Метод-расширение поверх класса типов
> Расширение объявлено для любого типа `A`, но требует наличия реализации `Show[A]`. Без неё вызов не скомпилируется.
>
> Ожидаемый результат: `42.show` возвращает `"42"`; вызов `.show` на типе без реализации `Show` — ошибка компиляции.
>
> ```scala
> extension [A](a: A)
>   def show(using s: Show[A]): String =
>     s.show(a)
>
> 42.show // "42"
> ```
>
> Пример показывает: зачем нужна третья часть паттерна — поведение вызывается как обычный метод типа.

---

## Отличие от ООП-наследования

| Характеристика | Наследование интерфейса | Класс типов |
|---|---|---|
| Где объявлено поведение | В самом классе | Отдельно от класса |
| Чужие типы | Требуется изменить исходный код | Изменения не нужны |
| Данные и поведение | Совмещены | Разделены |
| Момент проверки | Компиляция | Компиляция |

---

## Готовые классы типов

На практике собственные классы типов создают нечасто — обычно используют готовые:

- `Ordering[A]` — правило сравнения. При вызове `.sorted` компилятор ищет реализацию для типа элементов списка.
- Сериализация в JSON. Библиотеки для работы с API описывают этим паттерном правила преобразования case-класса в JSON; сама сериализация — подробнее в продвинутом курсе.

## Запись в Scala 2

В Scala 2 роль `given` и `using` выполняло ключевое слово `implicit`. Части паттерна те же.

##### Интерфейс

Первая часть совпадает с версией для Scala 3.

> [!example]- Пример: Интерфейс в Scala 2
> Объявление трейта не зависит от версии языка.
>
> Ожидаемый результат: объявлен тип `Show[A]` с методом `show`.
>
> ```scala
> trait Show[A] {
>   def show(a: A): String
> }
> ```
>
> Пример показывает: почему миграция паттерна проста — меняется только способ объявления реализации.

##### Реализация

> [!example]- Пример: Реализация через implicit val
> Вместо `given` объявляется `implicit val` с явно указанным типом.
>
> Ожидаемый результат: компилятор находит `intShow` при поиске реализации `Show[Int]`.
>
> ```scala
> implicit val intShow: Show[Int] = new Show[Int] {
>   def show(a: Int): String = a.toString
> }
> ```
>
> Пример показывает: чем запись Scala 2 отличается от Scala 3 — реализации требуется имя, хотя поиск идёт по типу.

##### Синтаксис использования

> [!example]- Пример: Расширение через implicit class
> Роль `extension` играет `implicit class`, принимающий реализацию неявным параметром.
>
> Ожидаемый результат: `42.show` возвращает `"42"` — так же, как в версии для Scala 3.
>
> ```scala
> implicit class ShowOps[A](val a: A) extends AnyVal {
>   def show(implicit s: Show[A]): String = s.show(a)
> }
> ```
>
> Пример показывает: почему обе записи встречаются в реальном коде — механика поиска реализации одна и та же.
