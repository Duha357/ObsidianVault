## Утиная типизация (Structural Types)

---

## Идея: «Важно что есть, а не кто это»

В строгих языках, если бы мы хотели написать общий метод закрытия ресурсов, то мы бы объявили интерфейс Closeable и использовали бы его для классов (implements Closeable). Но бывают ситуации, когда у нескольких классов извне нет общего интерфейса, но есть метод close() с одинаковой сигнатурой. Тогда нам бы пришлось писать 2 метода.

Scala поддерживает принцип утиной типизации: если объект выглядит как утка, то он и есть утка.

Для компилятора становится важна не родословная объекта (от кого унаследован), а его структура - наличие конкретных методов.

---

## Как это пишется

В Scala можно создать тип данных, который описывается не именем класса, а набором методов внутри фигурных скобок. Он называется структурным типом.

Данный код означает: мне подойдет любой объект, у которого есть метод close с такими параметрами и возвращаемым значением.

type Closable = {  
  def close(): Unit  
}

Теперь можно написать универсальную функцию. К примеру, она просто будет вызывать метод у переданного объекта. Этот код примет и файл, и сетевое соединение, хотя они никак не связаны, у них даже нет общего интерфейса.

class EBookFile:

  def close(): Unit = println("Файл закрыт")

  

class DbConnection:

  def close(): Unit = println("Соединение закрыто")

  

def closeResource(r: Closable): Unit = r.close()

  

closeResource(EBookFile())        // Выведет: Файл закрыт

closeResource(DbConnection()) // Выведет: Соединение закрыто

## Проблемы производительности

Структурные типы выглядят достаточно удобно для использования и позволяют работать с классами извне. Но, в отличие от расширений и классов типов, у структурных типов есть огромный минус - использование Java Reflection. Рефлексия нужна, поскольку в момент выполнения программы нужно найти и вызвать нужный метод у неизвестного объекта.

Это работает значительно медленнее, чем обычный вызов метода объекта. Поэтому структурные типы используются редко, в основном для написания быстрых обёрток над legacy-кодом. В высоконагруженном коде не рекомендуется использовать этот паттерн.

Структурные типы vs Классы типов

Вы могли заметить, что оба паттерна работают с одинаковой проблемой: как работать с классами из чужих библиотек без изменения их кода.

Но сейчас программисты почти всегда выбирают классы типов из прошлой главы. Вот основные причины, почему это лучше:

- Они работают на этапе компиляции (не случится ошибки во время выполнения)
    
- Они не используют медленный Reflection.
