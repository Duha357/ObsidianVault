Структурный тип описывается не именем класса, а набором методов: подойдёт любой объект нужной формы, независимо от того, от кого он унаследован. Это принцип утиной типизации — «если объект выглядит как утка, значит, это утка». Цена такой гибкости — обращение к методам через Java Reflection во время выполнения. Ниже: синтаксис структурных типов, их ограничения и сравнение с классами типов.

---

## Идея: важно, что есть, а не кто это

Задача: написать общий метод закрытия ресурсов. В строгих языках для этого объявляют интерфейс `Closeable` и реализуют его в каждом классе. Но если классы пришли из чужих библиотек, общего интерфейса у них нет — есть только одинаковый метод `close()`.

Для компилятора Scala в этом случае важна не родословная объекта, а его структура: наличие конкретных методов с нужными сигнатурами.

---

## Синтаксис структурного типа

Тип объявляется перечислением методов в фигурных скобках. Ключевое слово `type` задаёт имя для типа — так же, как `val` задаёт имя для значения.

> [!example]- Пример: Объявление структурного типа
> `type Closeable = { ... }` вводит имя для описания «объект с методом `close`». Тип означает: подойдёт любой объект, у которого есть метод `close` без параметров и без результата.
>
> Ожидаемый результат: объявлен тип `Closeable`, не связанный ни с одной иерархией классов.
>
> ```scala
> type Closeable = {
>   def close(): Unit
> }
> ```
>
> Пример показывает: зачем нужны структурные типы — требование к объекту описывается набором методов, а не именем класса.

> [!example]- Пример: Использование структурного типа
> Функция принимает любой объект, удовлетворяющий структуре. Два переданных класса ничем не связаны и не имеют общего родителя.
>
> Ожидаемый результат: печатается `File closed`, затем `Connection closed` — обе реализации подошли под один тип.
>
> ```scala
> import reflect.Selectable.reflectiveSelectable // требуется для структурных типов
>
> class EBookFile:
>   def close(): Unit = println("File closed")
>
> class DbConnection:
>   def close(): Unit = println("Connection closed")
>
> def closeResource(resource: Closeable): Unit = resource.close()
>
> closeResource(EBookFile())    // File closed
> closeResource(DbConnection()) // Connection closed
> ```
>
> Пример показывает: для чего нужна утиная типизация — общий код работает с классами, которые не планировали быть совместимыми.

## Проблема производительности

Главный минус структурных типов — использование Java Reflection. Во время выполнения нужный метод ищется у объекта по имени, потому что статически он неизвестен.

> [!example]- Пример: Плохо — структурный тип в горячем коде
> Вызов внутри цикла проходит через рефлексию на каждой итерации: поиск метода по имени выполняется заново.
>
> Ожидаемый результат: результат верный, но вызов обходится в десятки раз дороже обычного вызова метода.
>
> ```scala
> def closeAll(resources: List[Closeable]): Unit =
>   resources.foreach(_.close()) // каждый вызов идёт через рефлексию
> ```
>
> Пример показывает: для чего знать про рефлексию — структурный тип незаметно меняет стоимость обычного на вид вызова.

> [!example]- Пример: Хорошо — общий трейт вместо структурного типа
> Общее поведение объявлено трейтом и подмешано к обоим классам. Вызов становится обычным полиморфным вызовом, без рефлексии.
>
> Ожидаемый результат: тот же вывод, но метод вызывается напрямую.
>
> ```scala
> trait Closeable:
>   def close(): Unit
>
> class EBookFile extends Closeable:
>   def close(): Unit = println("File closed")
>
> class DbConnection extends Closeable:
>   def close(): Unit = println("Connection closed")
> ```
>
> Пример показывает: почему структурные типы применяют редко — если код классов доступен, обычный трейт решает задачу дешевле.

Основная область применения структурных типов — быстрые обёртки над legacy-кодом. В высоконагруженном коде их использовать не рекомендуется.

---

## Структурные типы против классов типов

Оба паттерна решают одну задачу: как работать с классами из чужих библиотек, не меняя их код. На практике почти всегда выбирают классы типов (раздел 3.3.2).

| Характеристика | Структурные типы | Классы типов |
|---|---|---|
| Проверка соответствия | Компиляция, вызов — рефлексия | Компиляция |
| Стоимость вызова | Высокая из-за рефлексии | Обычный вызов метода |
| Гибкость требований | Только набор методов | Произвольное поведение |
| Частота применения | Редко | Стандартный выбор |
