Состояние в функциональном стиле не хранится в изменяемой переменной, а передаётся: функция принимает текущее состояние и возвращает результат вместе с новым состоянием. Приём называется state threading — «протягивание состояния». Ниже: чем плохо глобальное изменяемое состояние, как выглядит его функциональная замена и в какую проблему упирается ручная передача.

---

## Проблема изменяемого состояния

В императивном стиле состояние программы живёт в переменных, которые меняются по ходу выполнения.

> [!example]- Пример: Плохо — глобальный изменяемый счётчик
> Идентификаторы новых книг выдаёт функция, которая читает и меняет переменную вне себя. По значению `lastId` нельзя понять, кто и сколько раз её вызывал.
>
> Ожидаемый результат: последовательные вызовы дают 1, 2, 3; из двух потоков часть значений совпадёт или пропадёт.
>
> ```scala
> var lastId = 0
>
> def nextId(): Int =
>   lastId = lastId + 1 // читаем и меняем внешнюю переменную
>   lastId
> ```
>
> Пример показывает: для чего состояние выносят в параметры — иначе результат зависит от истории вызовов, а не от входных данных.

Проблемы такого кода: поведение непредсказуемо, тест требует сброса состояния перед каждым запуском, а в многопоточной среде возникают гонки.

---

## Функциональный подход: передача состояния

Чтобы обойтись без изменяемых переменных, функция возвращает не только результат, но и новое состояние. Вызывающий код сам решает, что делать с этим состоянием дальше.

> [!example]- Пример: Контракт генератора
> Метод возвращает кортеж: сам идентификатор и генератор, из которого получится следующий. Изменяемых полей в контракте нет.
>
> Ожидаемый результат: тип результата `(Int, IdGenerator)` описывает и значение, и продолжение — по сигнатуре видно, что состояние передаётся наружу.
>
> ```scala
> trait IdGenerator:
>   def nextId: (Int, IdGenerator) // значение и новое состояние
> ```
>
> Пример показывает: зачем возвращать состояние из функции — так требование «продолжить с новым состоянием» попадает в тип.

> [!example]- Пример: Хорошо — реализация через новый объект
> Реализация не меняет своё поле, а создаёт новый генератор с увеличенным идентификатором.
>
> Ожидаемый результат: `LibraryIdGenerator(0).nextId` возвращает `(1, LibraryIdGenerator(1))`; исходный объект остаётся с `currentId = 0`.
>
> ```scala
> case class LibraryIdGenerator(currentId: Int) extends IdGenerator:
>   def nextId: (Int, IdGenerator) =
>     val newId = currentId + 1
>     val nextGenerator = LibraryIdGenerator(newId) // новое состояние, не мутация
>     (newId, nextGenerator)
> ```
>
> Пример показывает: почему изменяемое поле не нужно — новое состояние выражается новым объектом.

## Использование

> [!example]- Пример: Последовательное получение идентификаторов
> Каждый вызов возвращает пару, из которой берётся значение и генератор для следующего шага.
>
> Ожидаемый результат: `id1` — 1, `id2` — 2; `gen1` по-прежнему хранит `currentId = 0`, поэтому повторный `gen1.nextId` снова вернёт 1.
>
> ```scala
> val gen1 = LibraryIdGenerator(0)
>
> val (id1, gen2) = gen1.nextId // id1 = 1, gen2 хранит currentId = 1
> val (id2, gen3) = gen2.nextId // id2 = 2, gen3 хранит currentId = 2
> ```
>
> Пример показывает: зачем нужна воспроизводимость — от одного и того же генератора всегда получается один и тот же результат.

Что это даёт:

- Результат полностью определяется начальным состоянием, поэтому сценарий воспроизводится в тесте.
- Общей изменяемой переменной нет, поэтому нет и гонок между потоками.

## Проблема «state hell»

У ручной передачи состояния есть цена. Если идентификаторов нужно много и каждый следующий зависит от предыдущего, код превращается в цепочку промежуточных значений.

> [!example]- Пример: Плохо — ручная цепочка состояний
> Каждый шаг вводит новое имя генератора. Ошибиться и передать в следующий вызов старое состояние легко, а компилятор этого не заметит.
>
> Ожидаемый результат: значения получены верно, но имена `g1`, `g2`, `g3` не несут смысла и растут вместе с количеством шагов.
>
> ```scala
> val (firstId, g1) = generator.nextId
> val (secondId, g2) = g1.nextId
> val (thirdId, g3) = g2.nextId
> // ... и так далее
> ```
>
> Пример показывает: для чего существует монада состояния — ручная передача не масштабируется на длинные цепочки.

Такое явление называют «state hell» — ад состояний. Причина в том, что состояние передаётся вручную. В продвинутом функциональном программировании задачу решает монада состояния (State Monad), обычно берут готовую реализацию из библиотеки Cats.

В рамках базового курса её устройство не разбирается — важно понимать саму проблему.
