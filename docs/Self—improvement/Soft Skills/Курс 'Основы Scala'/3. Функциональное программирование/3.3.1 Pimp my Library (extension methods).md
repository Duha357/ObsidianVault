Методы-расширения позволяют добавить метод к уже существующему типу — включая финальные классы JDK, которые нельзя наследовать. Исходный код типа при этом не меняется: метод объявляется отдельно и подключается компилятором в месте вызова. Ниже: проблема закрытых классов, синтаксис `extension` в Scala 3, применение для DSL и то, как та же задача решалась в Scala 2.

---

## Проблема закрытых классов

Задача: проверить, является ли строка ISBN-номером книги. Естественное решение — добавить метод в `String`, но этот класс объявлен как `final`, унаследоваться от него нельзя.

> [!example]- Пример: Плохо — утилитный объект
> Проверка вынесена в отдельный объект, поэтому вызов идёт «наизнанку»: сначала имя утилиты, потом проверяемое значение.
>
> Ожидаемый результат: `true`; при нескольких таких проверках подряд вызовы вкладываются друг в друга и читаются справа налево.
>
> ```scala
> StringUtils.isISBN("978-5-17-180326-1") // true
> ```
>
> Пример показывает: для чего нужны методы-расширения — утилитный объект разрывает естественный порядок чтения.

> [!example]- Пример: Хорошо — метод-расширение
> Блок `extension` объявляет, к какому типу добавляется метод. Вызов выглядит так, будто метод всегда был частью `String`.
>
> Ожидаемый результат: `"978-5-389-02083-2".isISBN` — `true`, `"123-qwerty".isISBN` — `false`. Исходный код `String` при этом не изменился.
>
> ```scala
> extension (value: String) // value — значение, к которому применяется метод
>   def isISBN: Boolean =
>     value.startsWith("978-") || value.startsWith("979-")
>
> println("978-5-389-02083-2".isISBN) // true
> println("123-qwerty".isISBN)        // false
> ```
>
> Пример показывает: зачем нужен `extension` — поведение добавляется к чужому типу без наследования и правки его кода.

Похожая возможность есть в C# и Kotlin, где она называется extension methods.

## Построение DSL

Методы-расширения позволяют задать синтаксис под конкретную предметную область — внутренний DSL (Domain Specific Language).

> [!example]- Пример: Единицы измерения через расширение
> Метод добавляется к типу `Int`, поэтому число получает читаемую единицу измерения прямо в коде.
>
> Ожидаемый результат: `5.seconds` возвращает `5000L` — количество миллисекунд.
>
> ```scala
> extension (count: Int)
>   def seconds: Long = count * 1000L
>
> val timeout = 5.seconds // 5000L
> ```
>
> Пример показывает: для чего строят DSL — выражение читается как фраза предметной области, а не как вызов функции.

## Как это делалось в Scala 2

До появления `extension` расширения объявляли через `implicit class`.

> [!example]- Пример: Плохо — implicit class без оптимизации
> Класс-обёртка создаётся при каждом вызове метода. Для часто вызываемого расширения это лишние объекты и нагрузка на сборщик мусора.
>
> Ожидаемый результат: `5.seconds` возвращает `5000L`, но каждый вызов создаёт экземпляр `IntOps`.
>
> ```scala
> implicit class IntOps(val count: Int) {
>   def seconds: Long = count * 1000L
> }
> ```
>
> Пример показывает: для чего понадобилась оптимизация — обёртка стоит одного объекта на каждый вызов.

> [!example]- Пример: Хорошо — implicit class extends AnyVal
> `extends AnyVal` заставляет компилятор обрабатывать обёртку как примитивное значение: метод превращается в обычный статический вызов, объект не создаётся.
>
> Ожидаемый результат: тот же `5000L`, но без выделения памяти под обёртку.
>
> ```scala
> implicit class IntOps(val count: Int) extends AnyVal {
>   def seconds: Long = count * 1000L
> }
> ```
>
> Пример показывает: почему в коде на Scala 2 у расширений почти всегда стоит `extends AnyVal` — иначе теряется производительность.

Оптимизация применима при трёх условиях:

1. У класса ровно один параметр — важен именно его тип.
2. Параметр объявлен как `val`, а не `var`.
3. Класс не является вложенным, и от него не наследуются.

В Scala 3 эти ограничения не нужны: `extension` по определению не создаёт обёртку.
