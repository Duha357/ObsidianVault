Три близких по названию, но разных механизма: частичное применение фиксирует часть аргументов, `PartialFunction` описывает функцию, определённую не для всех входов, а каррирование превращает функцию нескольких аргументов в цепочку функций одного. Связывает их синтаксис групп параметров — нескольких списков аргументов у одной функции. Ниже: каждый механизм по отдельности и то, зачем группы параметров нужны для вывода типов и контекстных абстракций.

---

## Частичное применение (Partial Application)

Частичное применение фиксирует часть аргументов и возвращает функцию с меньшим числом параметров. Исходная функция при этом не меняется.

> [!example]- Пример: Фиксация одного аргумента
> Подчёркивание на месте второго аргумента означает «этот параметр останется незаполненным».
>
> Ожидаемый результат: `addLibraryBooks` имеет тип `Int => Int`; `addLibraryBooks(50)` возвращает 150.
>
> ```scala
> def addBooks(firstShelf: Int, secondShelf: Int): Int = firstShelf + secondShelf
>
> val addLibraryBooks: Int => Int = addBooks(100, _) // первый аргумент зафиксирован
>
> addLibraryBooks(50) // 150
> ```
>
> Пример показывает: зачем частичное применение — часто повторяющийся аргумент задаётся один раз.

##### Это не PartialFunction

Частично применённая функция — обычная функция:

- Определена для всех допустимых входов.
- **Не:**
    - Содержит логику «определено / не определено».
    - Связана с типом `PartialFunction`.

---

## Частично определённые функции (PartialFunction)

`PartialFunction[A, B]` — функция, определённая не для всех значений типа `A`.

> [!example]- Пример: Объявление PartialFunction
> Тело состоит только из веток `case`. Значения, не совпавшие ни с одной веткой, лежат вне области определения.
>
> Ожидаемый результат: функция определена для 1 и 2; вызов `bookCategory(3)` выбрасывает `MatchError`.
>
> ```scala
> val bookCategory: PartialFunction[Int, String] =
>   case 1 => "Fantasy"
>   case 2 => "Science Fiction"
> ```
>
> Пример показывает: зачем отдельный тип — он сообщает вызывающему коду, что функция покрывает не все входы.

##### Методы PartialFunction

Ключевых методов два: `isDefinedAt(a: A): Boolean` проверяет область определения, `apply(a: A): B` вычисляет значение.

> [!example]- Пример: Плохо — вызов без проверки
> Функция вызывается со значением, для которого не определена.
>
> Ожидаемый результат: `MatchError` во время выполнения — ошибка не отличается по последствиям от `NullPointerException`.
>
> ```scala
> bookCategory(5) // MatchError
> ```
>
> Пример показывает: для чего нужна проверка области определения — без неё частичная функция ведёт себя как мина.

> [!example]- Пример: Хорошо — проверка через isDefinedAt
> Перед вызовом проверяется, покрывает ли функция это значение.
>
> Ожидаемый результат: `isDefinedAt(1)` — `true`, `isDefinedAt(5)` — `false`.
>
> ```scala
> bookCategory.isDefinedAt(1) // true
> bookCategory.isDefinedAt(5) // false
> ```
>
> Пример показывает: зачем `isDefinedAt` — он позволяет узнать применимость функции, не вызывая её.

##### orElse

`orElse` объединяет частичные функции: результат определён, если определена хотя бы одна из них.

> [!example]- Пример: Объединение через orElse
> Две узкие функции соединяются в одну более широкую. Порядок важен: проверяется сначала первая.
>
> Ожидаемый результат: `allCategories` определена для 1 и 2.
>
> ```scala
> val fictionCategory: PartialFunction[Int, String] =
>   case 1 => "Fantasy"
>
> val scienceCategory: PartialFunction[Int, String] =
>   case 2 => "Science Fiction"
>
> val allCategories = fictionCategory.orElse(scienceCategory)
> ```
>
> Пример показывает: для чего нужен `orElse` — правила описываются по отдельности и собираются в общую таблицу.

##### Где применяются

- Метод `collect` у коллекций: обрабатывает только подходящие элементы.
- Декларативное описание наборов правил, где каждое правило покрывает свою часть входов.

> [!example]- Пример: collect
> `collect` за один проход отбирает подходящие элементы и преобразует их. Ветка `case` с условием задаёт и фильтр, и преобразование.
>
> Ожидаемый результат: `List(250, 400)` — элемент 100 не прошёл условие, 200 и 350 увеличены на 50.
>
> ```scala
> List(100, 200, 350).collect:
>   case pages if pages > 150 => pages + 50
> ```
>
> Пример показывает: зачем `collect` — он заменяет пару `filter` и `map` одной операцией.

## Каррирование

Каррирование — преобразование функции нескольких аргументов в цепочку функций одного аргумента: тип `(A, B) => C` превращается в `A => B => C`.

> [!example]- Пример: Каррированная форма записи
> Аргументы объявлены двумя списками, поэтому вызов можно оборвать после первого — результатом будет функция.
>
> Ожидаемый результат: `calculatePages(3)` возвращает функцию `Int => Int`; `pagesForThreeBooks(200)` возвращает 600.
>
> ```scala
> def calculatePages(bookCount: Int)(pagesPerBook: Int): Int = bookCount * pagesPerBook
>
> val pagesForThreeBooks = calculatePages(3) // Int => Int
> pagesForThreeBooks(200) // 600
> ```
>
> Пример показывает: зачем каррирование — фиксация первого аргумента не требует ни подчёркиваний, ни обёрток.

Готовое функциональное значение каррируется методом `.curried`.

> [!example]- Пример: Метод .curried
> Функциональное значение с двумя параметрами преобразуется в цепочку.
>
> Ожидаемый результат: тип `(Int, Int) => Int` превращается в `Int => Int => Int`.
>
> ```scala
> val multiplyPages: (Int, Int) => Int = _ * _
> val curriedPages = multiplyPages.curried
> ```
>
> Пример показывает: для чего нужен `.curried` — он даёт каррированную форму без переписывания объявления.

## Группы параметров

Scala позволяет объявлять функцию с несколькими списками параметров. Это влияет на каррирование, вывод типов, частичное применение и контекстные абстракции.

> [!example]- Пример: Две группы параметров
> Аргументы разнесены по двум спискам вместо одного.
>
> Ожидаемый результат: `calculateShelfCapacity(5)(20)` возвращает 100.
>
> ```scala
> def calculateShelfCapacity(rows: Int)(booksPerRow: Int): Int = rows * booksPerRow
> ```
>
> Пример показывает: как выглядит синтаксис, на котором основаны все дальнейшие приёмы.

##### Улучшение вывода типов

Типы выводятся по группам слева направо: то, что определилось в первой группе, доступно при разборе второй.

> [!example]- Пример: Плохо — один список параметров
> Значение и функция объявлены в одной группе, поэтому на момент разбора лямбды тип `A` ещё не определён. Тип параметра лямбды приходится писать вручную.
>
> Ожидаемый результат: `applyTo(320, book => book.toString)` не компилируется без явной аннотации `(book: Int)`.
>
> ```scala
> def applyTo[A, B](a: A, f: A => B): B = f(a)
>
> applyTo(320, (book: Int) => s"Pages: $book") // тип параметра указан вручную
> ```
>
> Пример показывает: для чего аргументы разносят по группам — в одном списке вывод типов работает хуже.

> [!example]- Пример: Хорошо — две группы параметров
> Тип `A` определяется по первой группе, поэтому во второй компилятор уже знает тип параметра лямбды.
>
> Ожидаемый результат: `applyTo(320)(book => s"Pages: $book")` компилируется без аннотаций и возвращает `"Pages: 320"`.
>
> ```scala
> def applyTo[A, B](a: A)(f: A => B): B = f(a)
>
> applyTo(320)(book => s"Pages: $book") // тип book выведен как Int
> ```
>
> Пример показывает: зачем группы параметров на практике — они убирают ручные аннотации типов в лямбдах.

##### Отложенное вычисление аргумента

Вторая группа часто содержит блок кода. Запись `=> Unit` означает by-name параметр: выражение передаётся невычисленным и выполняется внутри функции.

> [!example]- Пример: Блок кода во второй группе
> `action` объявлен как by-name параметр, поэтому вычисляется не при вызове, а в момент обращения внутри тела.
>
> Ожидаемый результат: сначала печатается сообщение, затем выполняется переданный блок.
>
> ```scala
> def withLogger(message: String)(action: => Unit): Unit =
>   println(message)
>   action // вычисление происходит здесь
>
> withLogger("Lending a book"):
>   println("Dune is lent to the reader")
> ```
>
> Пример показывает: почему такой вызов читается как встроенная конструкция языка — блок кода передаётся отдельной группой параметров.

##### Связь с контекстными параметрами

Отдельная группа параметров отделяет бизнес-аргументы от контекстных, объявляемых через `using`:

- Первая группа — данные, с которыми работает функция.
- Вторая группа — контекст выполнения.

Это фундамент паттерна Type Classes, к которому курс возвращается в разделе 1.4.5.

## Сравнение понятий

| Концепция | Смысл |
|---|---|
| Частичное применение | Фиксация части аргументов |
| `PartialFunction` | Функция, определённая не для всех входов |
| Каррирование | Преобразование в цепочку функций одного аргумента |
| Группы параметров | Синтаксис, на котором держатся каррирование и вывод типов |
