Scala — гибридный язык: ООП и ФП не противопоставлены, а объединены в одной языковой модели. Парадигма выбирается под задачу, а не под язык. Ниже: как выражены объектно-ориентированные и функциональные средства, как они дополняют друг друга и почему Scala 3 не навязывает одну парадигму.

---

## Два аспекта одной модели

##### Объектно-ориентированный аспект

- Каждое значение является объектом.
- Поведение и данные инкапсулируются в классах.
- Поддерживаются наследование, полиморфизм и инкапсуляция.
- Поведение композируется через трейты и миксины.

Объектная модель совместима с Java и знакома разработчикам классических ООП-языков.

##### Функциональный аспект

- Функции являются значениями первого класса.
- Широко применяются функции высшего порядка.
- Поощряется неизменяемость данных.
- Активно используется сопоставление с образцом (pattern matching).
- Стандартная библиотека ориентирована на декларативную обработку данных.

Функциональные возможности встроены в синтаксис и систему типов, а не добавлены библиотекой.

## Поддержка объектно-ориентированного программирования

##### Инкапсуляция

Внутреннее состояние скрывается модификатором `private`, а изменяется только через методы, которые проверяют корректность операции.

> [!example]- Пример: Плохо — открытое поле
> Поле `copies` объявлено без `private`, поэтому его меняет любой внешний код. Проверить условие «добавляем неотрицательное количество» негде.
>
> Ожидаемый результат: `book.copies = -100` компилируется и оставляет объект в невозможном состоянии — отрицательное число экземпляров книги.
>
> ```scala
> class LibraryBook(var copies: Int) // поле открыто на запись
>
> val book = LibraryBook(10)
> book.copies = -100 // объект попал в некорректное состояние
> ```
>
> Пример показывает: для чего нужна инкапсуляция — без неё инвариант объекта защищать нечем.

> [!example]- Пример: Хорошо — состояние за методами
> Поле `copies` закрыто, изменение идёт через `addCopies`, который отбрасывает некорректный аргумент.
>
> Ожидаемый результат: `addCopies(5)` доводит `copies` до 15, `getCopies` возвращает 15, обращение к `copies` снаружи — ошибка компиляции.
>
> ```scala
> class LibraryBook(private var copies: Int):
>   def addCopies(amount: Int): Unit =
>     if amount > 0 then // проверка перед изменением состояния
>       copies += amount
>
>   def getCopies: Int = copies
> ```
>
> Пример показывает: почему состояние прячут за методами — объект сам отвечает за собственную корректность.

##### Наследование

Наследование расширяет или специализирует поведение базового типа и переиспользует код.

> [!example]- Пример: Специализация поведения через наследование
> `Novel` наследует `Book` и переопределяет `genre`. Ключевое слово `override` в Scala обязательно, в отличие от Java.
>
> Ожидаемый результат: `Novel().genre` возвращает `"fiction"` вместо унаследованного `"unknown"`.
>
> ```scala
> class Book:
>   def genre: String = "unknown"
>
> class Novel extends Book:
>   override def genre: String = "fiction" // override обязателен
> ```
>
> Пример показывает: зачем наследование — подкласс меняет только отличающуюся часть поведения.

Композиция через трейты дополняет или заменяет наследование и снижает жёсткость иерархий. Подробнее — в разделе 2.1.2.

##### Полиморфизм

Полиморфизм позволяет работать с объектами разных классов через общий базовый тип. Реализация метода выбирается по фактическому типу объекта во время выполнения.

> [!example]- Пример: Выбор реализации по фактическому типу
> Переменная объявлена с типом `Book`, а хранит экземпляр `Novel`. Функция `printGenre` знает только о `Book`.
>
> Ожидаемый результат: печатается `fiction` — реализация берётся из `Novel`, а не из `Book`.
>
> ```scala
> def printGenre(book: Book): Unit =
>   println(book.genre)
>
> val novel: Book = Novel() // тип переменной Book, объект — Novel
> printGenre(novel) // fiction
> ```
>
> Пример показывает: для чего нужен полиморфизм — новый подтип подключается без изменения вызывающего кода.

## Поддержка функционального программирования

##### Неизменяемость данных

Неизменяемое значение объявляется через `val`. Операции над коллекцией не меняют её, а возвращают новую.

> [!example]- Пример: Плохо — изменяемая коллекция
> `ListBuffer` меняется на месте. Тот, кто получил ссылку раньше, увидит изменение, которого не ждал.
>
> Ожидаемый результат: `books` и `sameBooks` — один и тот же объект, после `+=` оба содержат 4 элемента.
>
> ```scala
> import scala.collection.mutable.ListBuffer
>
> val books = ListBuffer("Scala Basics", "FP in Scala", "OOP Design")
> val sameBooks = books // копии нет, это та же коллекция
>
> books += "Design Patterns"
> println(sameBooks.length) // 4 — изменение «протекло» через ссылку
> ```
>
> Пример показывает: почему изменяемые коллекции опасны — состояние меняется там, где этого не ждут.

> [!example]- Пример: Хорошо — неизменяемая коллекция
> `List` неизменяем: `appended` создаёт новый список, исходный остаётся прежним.
>
> Ожидаемый результат: `books` — 3 элемента, `extendedBooks` — 4.
>
> ```scala
> val books = List("Scala Basics", "FP in Scala", "OOP Design")
> val extendedBooks = books.appended("Design Patterns") // новый список
>
> println(books.length)         // 3 — исходный не изменился
> println(extendedBooks.length) // 4
> ```
>
> Пример показывает: зачем неизменяемость — у значения нет скрытых изменений, его безопасно передавать куда угодно.

Неизменяемость уменьшает количество ошибок состояния, упрощает параллельное выполнение и делает код предсказуемым.

##### Чистые функции

Чистая функция зависит только от аргументов, не имеет побочных эффектов и для одинаковых аргументов всегда возвращает одинаковый результат.

> [!example]- Пример: Плохо — результат зависит от внешнего состояния
> Функция читает и меняет переменную `processedBooks`, объявленную снаружи.
>
> Ожидаемый результат: `countProcessed()` при одинаковом вызове возвращает 1, потом 2, потом 3 — тест на неё написать нельзя без сброса состояния.
>
> ```scala
> var processedBooks = 0
>
> def countProcessed(): Int =
>   processedBooks += 1 // побочный эффект: меняется внешняя переменная
>   processedBooks
> ```
>
> Пример показывает: для чего нужна чистота — иначе результат функции зависит от истории вызовов.

> [!example]- Пример: Хорошо — результат зависит только от аргументов
> `totalPages` не читает и не меняет ничего снаружи.
>
> Ожидаемый результат: `totalPages(150, 210)` возвращает 360 при любом числе вызовов и в любом порядке.
>
> ```scala
> def totalPages(firstBookPages: Int, secondBookPages: Int): Int =
>   firstBookPages + secondBookPages
> ```
>
> Пример показывает: почему чистые функции легко тестировать — достаточно подставить аргументы и сравнить результат.

##### Функции высшего порядка

Функции передаются как аргументы и возвращаются как результат. Это даёт переиспользуемые абстракции обработки данных.

> [!example]- Пример: Функция как аргумент
> `processPages` принимает не число, а правило обработки `pageRule`. Правило подставляется при вызове.
>
> Ожидаемый результат: `300` — `doublePages` вызвана внутри `processPages`.
>
> ```scala
> def processPages(count: Int, pageRule: Int => Int): Int =
>   pageRule(count)
>
> val doublePages = (pages: Int) => pages * 2
>
> println(processPages(150, doublePages)) // 300
> ```
>
> Пример показывает: зачем передавать функцию — алгоритм отделён от конкретного правила.

## Взаимодополняемость ООП и ФП

ООП и ФП не конкурируют, а решают разные задачи:

- ООП моделирует структуру системы и предметную область.
- ФП описывает логику и обработку данных.

> [!example]- Пример: Объектная модель и функциональная обработка
> `case class` описывает сущность домена, а `filter` и `map` обрабатывают список этих сущностей декларативно — без цикла и накопителя.
>
> Ожидаемый результат: `List(George Orwell, Jane Austen)` — отобраны авторы с 3 и более книгами, из них взяты имена.
>
> ```scala
> case class Author(name: String, books: Int)
>
> val authors = List(
>   Author("George Orwell", 6),
>   Author("Jane Austen", 8),
>   Author("Franz Kafka", 2)
> )
>
> val popularAuthors =
>   authors
>     .filter(author => author.books >= 3) // отбор
>     .map(author => author.name)          // преобразование
>
> println(popularAuthors) // List(George Orwell, Jane Austen)
> ```
>
> Пример показывает: почему парадигмы не конфликтуют — структуру задаёт ООП, обработку данных описывает ФП.

Код читается декларативно: описывает, что получить, а не как.

## Философия гибридности Scala 3

Scala 3 не навязывает строгую парадигму. Инструменты выбираются под задачу, приоритет — читаемость, надёжность и выразительность.

- **Не:**
    - Чистое функциональное программирование любой ценой.
    - Классическое ООП с повсеместным изменяемым состоянием.

Scala позволяет:

- Писать функционально чистый код там, где важны надёжность и предсказуемость.
- Использовать объектную модель и инкапсуляцию для сложных доменных структур.
- Комбинировать оба подхода без архитектурных конфликтов.
