Имя в Scala объявляется одним из двух способов: `val` — ссылку переназначить нельзя, `var` — можно. Тип при этом почти всегда пишет компилятор, а видимость имени определяется структурой кода. Ниже: различие `val` и `var`, почему `val` выбирают по умолчанию, вывод типов и правила областей видимости.

---

## Значения и переменные

Два способа объявления ссылок различаются только тем, разрешено ли переназначение.

> [!example]- Пример: Объявление val и var
> `libraryName` объявлено через `val`, `availableBooks` — через `var`. Синтаксис одинаковый, отличается ключевое слово.
>
> Ожидаемый результат: `libraryName` — `"City Library"`, `availableBooks` — `120`.
>
> ```scala
> val libraryName = "City Library"  // переназначить нельзя
> var availableBooks = 120          // переназначить можно
> ```
>
> Пример показывает: зачем два ключевых слова — изменяемость объявляется явно, а не подразумевается.

##### val — неизменяемая ссылка

`val` объявляет неизменяемую ссылку: имя всегда указывает на один и тот же объект.

> [!example]- Пример: Переназначение val
> Попытка присвоить новое значение имени, объявленному через `val`.
>
> Ожидаемый результат: ошибка компиляции «reassignment to val», программа не собирается.
>
> ```scala
> val mainAuthor = "Arthur Conan Doyle"
> mainAuthor = "Agatha Christie" // ошибка компиляции
> ```
>
> Пример показывает: почему `val` называют неизменяемым — компилятор запрещает переназначение.

Неизменяемой становится ссылка, но не обязательно сам объект. Если объект изменяемый, его внутреннее состояние по-прежнему меняется.

> [!example]- Пример: Плохо — val с изменяемым объектом
> Ссылка `shelf` закреплена, но `ListBuffer` — изменяемая коллекция. `val` защищает имя, а не содержимое.
>
> Ожидаемый результат: `shelf += "Dune"` компилируется и меняет коллекцию — в списке становится 4 элемента.
>
> ```scala
> import scala.collection.mutable.ListBuffer
>
> val shelf = ListBuffer("Dune", "Foundation", "Neuromancer")
> shelf += "Solaris" // допустимо: меняется объект, не ссылка
> ```
>
> Пример показывает: почему одного `val` мало — изменяемость объекта он не ограничивает.

> [!example]- Пример: Хорошо — val с неизменяемой коллекцией
> `List` неизменяем, поэтому `appended` не меняет исходную коллекцию, а возвращает новую.
>
> Ожидаемый результат: `shelf` — `List(Dune, Foundation, Neuromancer)`, `updatedShelf` — тот же список плюс `Solaris`.
>
> ```scala
> val shelf = List("Dune", "Foundation", "Neuromancer")
> val updatedShelf = shelf.appended("Solaris") // новый список
>
> println(shelf)        // List(Dune, Foundation, Neuromancer)
> println(updatedShelf) // List(Dune, Foundation, Neuromancer, Solaris)
> ```
>
> Пример показывает: зачем сочетать `val` и неизменяемую коллекцию — значение не меняется ни через имя, ни через объект.

##### var — изменяемая ссылка

`var` допускает переназначение. Поведение совпадает с переменными Java, C# и C++.

> [!example]- Пример: Переназначение var
> Счётчик выданных книг увеличивается на единицу.
>
> Ожидаемый результат: `borrowedBooks` становится 4.
>
> ```scala
> var borrowedBooks = 3
> borrowedBooks = borrowedBooks + 1
> ```
>
> Пример показывает: для чего нужен `var` — там, где значение обязано меняться во времени.

##### Философия Scala 3: val по умолчанию

Правило простое: `val` всегда, если нет строгой необходимости в `var`. Причины:

- Потокобезопасность: неизменяемое значение безопасно читать из нескольких потоков.
- Предсказуемость: нет скрытых изменений состояния.
- Упрощённое тестирование: меньше неявных зависимостей.
- Соответствие функциональной парадигме.

> [!example]- Пример: Плохо — var в общем состоянии
> Счётчик изменяется из нескольких потоков. Операция `+= 1` не атомарна: чтение, увеличение и запись выполняются раздельно.
>
> Ожидаемый результат: итоговое значение непредсказуемо и обычно меньше ожидаемого — часть увеличений теряется (race condition).
>
> ```scala
> var borrowedBooks = 0 // общее изменяемое состояние
>
> // два потока выполняют одно и то же
> borrowedBooks += 1
> borrowedBooks += 1
> ```
>
> Пример показывает: почему `var` опасен в конкурентном коде — состояние меняется одновременно из разных мест.

> [!example]- Пример: Хорошо — val вместо общего состояния
> Каждый поток возвращает результат, итог собирается сложением. Общего изменяемого состояния нет.
>
> Ожидаемый результат: `totalBorrowed` — 2 при любом порядке выполнения потоков.
>
> ```scala
> val firstThreadResult = 1
> val secondThreadResult = 1
>
> val totalBorrowed = firstThreadResult + secondThreadResult // 2
> ```
>
> Пример показывает: зачем предпочитать `val` — гонки невозможны, если менять нечего.

## Вывод типов (Type Inference)

Компилятор определяет тип по выражению справа от `=`. Тип при этом фиксируется так же жёстко, как если бы был написан вручную.

> [!example]- Пример: Объявление без аннотаций
> Тип не указан ни у одного значения.
>
> Ожидаемый результат: `bookCount` получает тип `Int` (целое число), `authorName` — `String` (строка).
>
> ```scala
> val bookCount = 42         // выведен тип Int
> val authorName = "Tolkien" // выведен тип String
> ```
>
> Пример показывает: почему аннотации типов в Scala редки — компилятор выводит их сам.

##### Когда указывать тип явно

Явная аннотация рекомендуется:

- Для публичных методов и API.
- При сложных обобщённых типах.
- Для улучшения читаемости.
- Когда нужно зафиксировать более узкий тип, чем вывел бы компилятор.

> [!example]- Пример: Явная аннотация типа
> Тип записан после имени через двоеточие — синтаксис `имя: Тип = значение`.
>
> Ожидаемый результат: `maxBooks` имеет тип `Int`, заданный явно.
>
> ```scala
> val maxBooks: Int = 42
> ```
>
> Пример показывает: для чего нужна аннотация — она фиксирует контракт там, где вывод типа не очевиден читателю.

##### Вывод типов не ослабляет проверку

Тип определяется один раз при инициализации и дальше не меняется.

> [!example]- Пример: Тип зафиксирован при инициализации
> Значение объявлено без аннотации, поэтому получило тип `Int`. Дальше ему пытаются присвоить строку.
>
> Ожидаемый результат: ошибка компиляции — `String` не подходит выведенному типу `Int`.
>
> ```scala
> var bookCount = 42
> bookCount = "many" // ошибка компиляции: ожидается Int
> ```
>
> Пример показывает: почему вывод типов не превращает Scala в динамический язык — проверка остаётся полной.

## Области видимости

Scala использует лексическую (статическую) область видимости: видимость имени определяется структурой кода.

- Вложенные блоки видят имена внешних блоков.
- **Не:**
    - Внешний код видит имена, объявленные внутри блока.

> [!example]- Пример: Границы области видимости
> `libraryName` объявлено снаружи, `sectionName` — внутри блока. Обращения идут в обе стороны.
>
> Ожидаемый результат: внутри блока `libraryName` доступно; `println(sectionName)` после блока — ошибка компиляции «not found».
>
> ```scala
> val libraryName = "Central Library"
>
> {
>   val sectionName = "Science Fiction"
>   println(libraryName) // доступно: имя из внешнего блока
> }
>
> println(sectionName) // ошибка компиляции: вне области видимости
> ```
>
> Пример показывает: зачем ограничивать видимость — временные имена не засоряют остальной код.

Вложенная функция видит имена внешней области так же, как вложенный блок.

> [!example]- Пример: Функция видит внешнее имя
> `totalShelves` объявлено снаружи, `sectionShelves` — внутри функции.
>
> Ожидаемый результат: `printShelves()` печатает 10 и 20; обращение к `sectionShelves` после вызова — ошибка компиляции.
>
> ```scala
> val totalShelves = 10
>
> def printShelves(): Unit =
>   val sectionShelves = 20
>   println(totalShelves)  // видит внешнее имя
>   println(sectionShelves)
>
> printShelves()
> println(sectionShelves) // ошибка компиляции
> ```
>
> Пример показывает: почему замыкание работает — функция помнит имена той области, где объявлена.

## Вложенность блоков

Блок `{ ... }` в Scala — не просто группа инструкций, а выражение: он вычисляется и возвращает значение последней строки.

> [!example]- Пример: Блок возвращает значение
> Блок объявляет два локальных значения и заканчивается их суммой. Результат присваивается `totalBooks`.
>
> Ожидаемый результат: `totalBooks` — 65 (40 + 25); `fictionBooks` и `historyBooks` снаружи недоступны.
>
> ```scala
> val totalBooks = {
>   val fictionBooks = 40
>   val historyBooks = 25
>   fictionBooks + historyBooks // последняя строка — результат блока
> }
> ```
>
> Пример показывает: для чего блок-выражение — промежуточные значения не выходят наружу, а результат вычисляется на месте.

Особенности:

- Блок возвращает значение последнего выражения.
- Блоки локализуют временные значения.
- **Не:**
    - Переменные внутри блока доступны снаружи.

## Перекрытие имён (Shadowing)

Shadowing — объявление во вложенной области имени, которое уже существует снаружи. Внешнее имя при этом не изменяется, а становится недоступным внутри.

> [!example]- Пример: Плохо — случайное перекрытие
> Внутри блока объявлено имя, совпадающее с внешним. Код читается так, будто значение изменилось, хотя внешнее имя не тронуто.
>
> Ожидаемый результат: внутри блока печатается `"Brave New World"`, после блока — снова `"1984"`.
>
> ```scala
> val bookTitle = "1984"
>
> {
>   val bookTitle = "Brave New World" // перекрывает внешнее имя
>   println(bookTitle) // Brave New World
> }
>
> println(bookTitle) // 1984
> ```
>
> Пример показывает: почему shadowing опасен — читатель ожидает изменения значения, а получает другое имя.

> [!example]- Пример: Хорошо — разные имена
> Локальное значение названо по смыслу, совпадений с внешним именем нет.
>
> Ожидаемый результат: печатается `"Brave New World"`, затем `"1984"`; какое значение откуда — видно из кода.
>
> ```scala
> val bookTitle = "1984"
>
> {
>   val recommendedTitle = "Brave New World"
>   println(recommendedTitle) // Brave New World
> }
>
> println(bookTitle) // 1984
> ```
>
> Пример показывает: для чего нужны осмысленные имена — они снимают двусмысленность без дополнительных правил.

Проблемы перекрытия имён:

- Ухудшение читаемости.
- Риск логических ошибок.
- Путаница при рефакторинге.
