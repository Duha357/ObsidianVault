Scala — статически типизированный язык общего назначения для JVM. Название от scalable («масштабируемый»): один язык и один стиль подходят и для небольшой утилиты, и для распределённой корпоративной системы, потому что ООП и ФП встроены в общую модель — класс и функция равноправны. Ниже: история языка, преемственность Scala 3 от Scala 2, ключевые характеристики и философия.

---

## История языка

Создан Мартином Одерски (Martin Odersky) и его командой, вышел в 2004 году. Scala 2 — 2006, Scala 3 — 2021.

Одерски участвовал в разработке generics для Java. Отсюда близость Scala к JVM и совместимость с существующим Java-кодом.

---

## Преемственность от Scala 2

Scala 3 — развитие Scala 2, не отдельный язык. Приоритет — обратная совместимость и миграция существующего кода.

Сохранено:

- Классы и объекты.
- Трейты как средство композиции поведения.
- Сопоставление с образцом (pattern matching).
- Функции как значения.
- Стандартная библиотека и коллекции.

Переработано:

- Система implicits — заменена на явные `given` и `using`.
- Синтаксис — меньше скобок и служебных слов.
- Сообщения об ошибках компилятора и диагностика.

Для миграции есть автоматизированные инструменты, например sbt-scala3-migrate.

## Ключевые характеристики языка

##### Интеграция с Java и JVM

Scala компилируется в байткод JVM, поэтому Java-библиотеки доступны напрямую — без обёрток и генерации кода.

- Классы Scala используют Java-библиотеки.
- Scala-классы наследуются от Java-классов и реализуют Java-интерфейсы.
- Scala внедряется в Java-проект поэтапно, файл за файлом.

> [!example]- Пример: Вызов Java-библиотеки из Scala
> Код использует `java.time.Year` из JDK напрямую: импорт такой же, как для класса Scala.
>
> Ожидаемый результат: `bookAge` — число лет с года издания книги.
>
> ```scala
> import java.time.Year // класс из JDK, не из стандартной библиотеки Scala
>
> val publicationYear = 1965
> val bookAge = Year.now().getValue - publicationYear
> ```
>
> Пример показывает: зачем совместимость с JVM — экосистема Java доступна как своя, переписывать её не нужно.

##### Функции как значения первого класса

Функция в Scala — обычное значение: её присваивают переменной, передают аргументом, возвращают из другой функции, хранят в коллекции. В Java для этого требовался интерфейс с единственным методом.

> [!example]- Пример: Функция как значение
> `totalPages` — не метод класса, а значение с типом `(Int, Int) => Int`.
>
> Ожидаемый результат: `500`.
>
> ```scala
> // (Int, Int) => Int — тип «принимает два Int, возвращает Int»
> val totalPages: (Int, Int) => Int = (firstBookPages, secondBookPages) => firstBookPages + secondBookPages
>
> println(totalPages(320, 210)) // 500
> ```
>
> Пример показывает: почему функции-значения заменяют класс-обёртку — поведение передаётся как обычные данные.

##### Функции высшего порядка

Функция высшего порядка принимает функцию параметром или возвращает её результатом. В параметр выносится не значение, а само действие.

> [!example]- Пример: Плохо — действие зашито в тело
> Правило пересчёта страниц вписано в функцию. Каждое новое правило требует отдельной копии функции.
>
> Ожидаемый результат: `300`; для правила «удвоить» придётся написать вторую такую же функцию.
>
> ```scala
> def addBonusTwice(pages: Int): Int =
>   (pages + 50) + 50 // правило «+50» зашито в тело
>
> println(addBonusTwice(200)) // 300
> ```
>
> Пример показывает: для чего нужен параметр-функция — без него код дублируется на каждое правило.

> [!example]- Пример: Хорошо — действие передано параметром
> `applyTwice` принимает правило `transform` и применяет его дважды. Правило задаётся при вызове.
>
> Ожидаемый результат: `300` — `addBonus` добавляет 50 страниц дважды.
>
> ```scala
> def applyTwice(pages: Int, transform: Int => Int): Int =
>   transform(transform(pages))
>
> val addBonus = (pages: Int) => pages + 50 // каждое переиздание добавляет 50 страниц
>
> println(applyTwice(200, addBonus)) // 300
> ```
>
> Пример показывает: зачем функции высшего порядка — одна реализация обслуживает любое правило.

##### Объекты как значения

`object` объявляет синглтон: единственный экземпляр создаёт сам язык. Используется как пространство имён, контейнер утилитных функций и точка входа программы. Как и функции, объект является значением.

> [!example]- Пример: Объект-синглтон как контейнер функций
> `LibraryCatalog` объявлен через `object`, поэтому экземпляр создавать не нужно. Метод `isLongRead` передан в `filter` как значение.
>
> Ожидаемый результат: `List(520, 670)` — книги толще 400 страниц.
>
> ```scala
> object LibraryCatalog: // аналог класса со static-методами в Java
>   def isLongRead(pages: Int): Boolean = pages > 400
>
> val books = List(150, 520, 380, 670)
> val longReads = books.filter(LibraryCatalog.isLongRead)
>
> println(longReads) // List(520, 670)
> ```
>
> Пример показывает: почему в Scala нет ключевого слова `static` — синглтон и утилиты выражаются одной конструкцией языка.

##### Строго статическая типизация и вывод типов

Типы проверяются на этапе компиляции, но записывать их вручную приходится редко: компилятор выводит тип из выражения.

> [!example]- Пример: Вывод типа значения
> Тип нигде не написан. Компилятор смотрит на значение справа от `=` и назначает тип сам.
>
> Ожидаемый результат: `pageCount` получает тип `Int` (целое число), `title` — тип `String` (строка). Присвоить им потом значение другого типа компилятор не даст.
>
> ```scala
> val pageCount = 320  // выведен тип Int
> val title = "Dune"   // выведен тип String
> ```
>
> Пример показывает: для чего нужен вывод типов — объявление короткое, как в динамическом языке, а проверка остаётся строгой.

> [!example]- Пример: Вывод типа результата функции
> После списка параметров не указано, что функция возвращает. Компилятор разбирает тело: интерполяция `s"..."` собирает строку — значит, результат строковый.
>
> Ожидаемый результат: функция считается возвращающей `String` (строку), хотя в коде этот тип не написан.
>
> ```scala
> // после `(title: String, author: String)` нет `: String` — тип результата выведен компилятором
> def formatBookEntry(title: String, author: String) = s"$title by $author"
> ```
>
> Пример показывает: почему сигнатуру не приходится дописывать вручную — тип результата компилятор берёт из тела функции.

> [!example]- Пример: Ошибка несовместимости типов
> Значение объявлено как `Int`, а инициализировано строкой.
>
> Ожидаемый результат: ошибка компиляции, программа не запускается.
>
> ```scala
> val pageCount: Int = "three hundred" // ошибка компиляции
> ```
>
> Пример показывает: зачем статическая проверка — несовпадение типов ловится до запуска, а не в проде.

## Философия языка

##### Снижение синтаксического шума

Scala 3 убирает служебные символы там, где структуру кода однозначно задаёт отступ.

> [!example]- Пример: Синтаксис Scala 2
> Тело метода в фигурных скобках, условие `if` — в круглых.
>
> Ожидаемый результат: `newerEdition(2019, 2020)` возвращает `2020`.
>
> ```scala
> def newerEdition(firstYear: Int, secondYear: Int): Int = {
>   if (firstYear > secondYear) firstYear else secondYear
> }
> ```
>
> Пример показывает: с чем сравнивается синтаксис Scala 3.

> [!example]- Пример: Синтаксис Scala 3
> Тот же метод без скобок: границы тела задаёт отступ, условие отделяет ключевое слово `then`.
>
> Ожидаемый результат: `newerEdition(2019, 2020)` возвращает `2020` — поведение не изменилось.
>
> ```scala
> def newerEdition(firstYear: Int, secondYear: Int): Int =
>   if firstYear > secondYear then firstYear else secondYear
> ```
>
> Пример показывает: зачем новый синтаксис — служебные символы убраны, смысл кода прежний.

Код без фигурных скобок и лишних служебных слов ближе к декларативному описанию логики.

##### Минимизация шаблонного кода

Высокоуровневые конструкции убирают повторяющийся код: описание данных сводится к объявлению полей.

> [!example]- Пример: Плохо — шаблонный код вручную
> Обычный класс требует ручного `toString`; `equals`, `hashCode` и копирование с изменением поля пришлось бы писать так же. Это аналог Java-класса до появления `record`.
>
> Ожидаемый результат: `Book(The Master and Margarita, Bulgakov, 1967, 480)`, но каждый метод написан руками.
>
> ```scala
> class Book(val title: String, val author: String, val year: Int, val pages: Int):
>   override def toString: String = s"Book($title, $author, $year, $pages)"
>   // equals, hashCode и копирование с изменением поля — тоже вручную
>
> val book = Book("The Master and Margarita", "Bulgakov", 1967, 480)
> println(book)
> ```
>
> Пример показывает: для чего нужен `case class` — без него каждый носитель данных обрастает одинаковым кодом.

> [!example]- Пример: Хорошо — case class
> Тот же тип объявлен одной строкой: конструктор, геттеры, `equals`, `hashCode`, `toString` и `copy` генерирует компилятор.
>
> Ожидаемый результат: `Book(The Master and Margarita, Bulgakov, 1967, 480)`.
>
> ```scala
> case class Book(title: String, author: String, year: Int, pages: Int)
>
> val book = Book("The Master and Margarita", "Bulgakov", 1967, 480) // new не требуется
> println(book)
> ```
>
> Пример показывает: почему `case class` — стандартный способ описывать данные в Scala: объявление сводится к одной строке.

`case class` автоматически генерирует:

- `equals` и `hashCode`.
- `toString`.
- Метод `copy`.
- Поддержку сопоставления с образцом.

##### Сопоставление с образцом (Pattern Matching)

`match` сравнивает не только значение, но и структуру объекта: проверка типа и извлечение полей выполняются одновременно.

> [!example]- Пример: Плохо — ручная проверка типа
> Тип проверяется через `isInstanceOf`, значение приводится через `asInstanceOf` — так разбор выглядит в языках без сопоставления с образцом.
>
> Ожидаемый результат: для `Book("Dune", "Herbert", 1965, 412)` — `"Book: 'Dune' by Herbert"`.
>
> ```scala
> def describeCatalogItem(item: Any): String =
>   if item.isInstanceOf[Book] then
>     val book = item.asInstanceOf[Book] // приведение типа вручную
>     s"Book: '${book.title}' by ${book.author}"
>   else if item.isInstanceOf[String] then
>     s"Author name: ${item.asInstanceOf[String]}"
>   else "Unknown catalog item"
> ```
>
> Пример показывает: для чего нужно сопоставление с образцом — ручная проверка типа многословна, а компилятор не контролирует её полноту.

> [!example]- Пример: Хорошо — сопоставление с образцом
> `match` за один проход определяет тип и разбирает объект: `title` и `author` извлекаются прямо в образце.
>
> Ожидаемый результат: для `Book("Dune", "Herbert", 1965, 412)` — `"Book: 'Dune' by Herbert"`; для строки — `"Author name: ..."`; для числа — `"Publication year: ..."`; иначе — `"Unknown catalog item"`.
>
> ```scala
> def describeCatalogItem(item: Any): String =
>   item match
>     case Book(title, author, _, _) => s"Book: '$title' by $author" // _ — поле не нужно
>     case author: String            => s"Author name: $author"
>     case year: Int                 => s"Publication year: $year"
>     case _                         => "Unknown catalog item"
> ```
>
> Пример показывает: зачем `match` — проверка типа и извлечение полей выполняются одной конструкцией.

Выигрыш заметнее на объектах и коллекциях, чем на строках и числах.

##### Метапрограммирование и вычисления во время компиляции

Метапрограммирование переносит часть вычислений и проверок с запуска на компиляцию.

> [!example]- Пример: Inline-раскрытие
> `inline` заставляет компилятор подставить тело функции в место вызова и вычислить его там же.
>
> Ожидаемый результат: в `memberPrice` на этапе компиляции записывается `450`.
>
> ```scala
> inline def discountedPrice(price: Int): Int = price - price / 10
>
> val memberPrice = discountedPrice(500) // компилятор подставит 500 - 500 / 10 = 450
> ```
>
> Пример показывает: зачем `inline` — вычисление уходит на этап компиляции, вызова при запуске не остаётся.

> [!example]- Пример: Плохо — проверка аргумента при запуске
> `require` проверяет значение во время выполнения, поэтому некорректный вызов доживает до запуска.
>
> Ожидаемый результат: код компилируется, но `checkPageCount(0)` падает с `IllegalArgumentException`.
>
> ```scala
> def checkPageCount(pages: Int): Int =
>   require(pages > 0, "Page count must be positive!")
>   pages
>
> checkPageCount(0) // ошибка при запуске
> ```
>
> Пример показывает: почему проверки при запуске недостаточно — ошибка обнаруживается уже у пользователя.

> [!example]- Пример: Хорошо — проверка на этапе компиляции
> `inline if` вычисляется компилятором, `error` прерывает компиляцию с заданным текстом.
>
> Ожидаемый результат: `requirePositivePageCount(0)` — ошибка компиляции с текстом `"Page count must be positive!"`.
>
> ```scala
> import scala.compiletime.error
>
> inline def requirePositivePageCount(inline pages: Int): Int =
>   inline if pages > 0 then pages else error("Page count must be positive!")
>
> requirePositivePageCount(0) // ошибка компиляции
> ```
>
> Пример показывает: зачем метапрограммирование — некорректный вызов не доживает до запуска.
