Scala — строго-статически типизированный язык: тип каждого выражения известен и проверен до запуска, а неявных преобразований между несовместимыми типами язык не выполняет. Типы здесь не формальность, а инструмент проектирования: ими описывают предметную область и запрещают некорректные состояния. Ниже: что значат «статическая» и «строгая», чем это отличается от других языков, что даёт на практике и как язык усиливает безопасность.

---

## Статическая и строгая типизация

##### Статическая типизация

- Типы всех выражений определяются и проверяются на этапе компиляции.
- Корректность операций между значениями проверяется до запуска программы.
- Программа с типовыми ошибками не компилируется.

> [!example]- Пример: Ошибка несовместимости типов
> Код складывает число и строку. В Python или JavaScript такая строка дожила бы до выполнения.
>
> Ожидаемый результат: ошибка компиляции «несовместимые типы Int и String», исполняемый файл не собирается.
>
> ```scala
> val bookCount: Int = 10
> val bookTitle: String = "Scala Basics"
>
> val result = bookCount + bookTitle
> // Ошибка компиляции: несовместимые типы Int и String
> ```
>
> Пример показывает: зачем статическая проверка — целый класс ошибок исчезает до запуска.

##### Строгая типизация

Строгая типизация означает, что язык не выполняет неявных и опасных преобразований: значения разных типов не смешиваются автоматически.

> [!example]- Пример: Плохо — слабая типизация
> В слабо типизированных языках оператор сам «догадывается», что делать с разнотипными операндами: для `+` строка побеждает, для `-` — число.
>
> Ожидаемый результат: `"5" + 2` даёт строку `"52"`, а `"5" - 2` — число `3`. Одна и та же пара операндов ведёт себя по-разному.
>
> ```javascript
> "5" + 2 // "52" — конкатенация
> "5" - 2 // 3    — вычитание
> ```
>
> Пример показывает: для чего нужна строгость — иначе результат операции зависит от неочевидных правил преобразования.

> [!example]- Пример: Хорошо — строгая типизация
> Scala не приводит `String` к числу и обратно молча. Преобразование пишется явно.
>
> Ожидаемый результат: `"5" - 2` — ошибка компиляции; чтобы получить `3`, нужно вызвать `toInt`.
>
> ```scala
> "5" - 2         // ошибка компиляции
> "5".toInt - 2   // 3 — преобразование указано явно
> ```
>
> Пример показывает: почему строгость важнее краткости — намерение разработчика записано в коде, а не угадывается языком.

## Сравнение с другими языками

| Язык | Типизация | Момент обнаружения ошибок |
|---|---|---|
| Python | Динамическая, строгая | Во время выполнения |
| JavaScript | Динамическая, слабая | Во время выполнения |
| Java | Статическая, строгая | Во время компиляции |
| Scala | Статическая, строгая | Во время компиляции |

Отличие Scala от Java: та же строгая статическая типизация сочетается с мощным выводом типов, поэтому код компактнее без потери безопасности.

## Преимущества строго-статической типизации

##### Раннее обнаружение ошибок

Ошибки типов — одна из самых распространённых категорий ошибок. В Scala они выявляются до запуска приложения.

> [!example]- Пример: Ошибка в аргументе вызова
> Функция объявлена для `String`, а вызвана с числом.
>
> Ожидаемый результат: ошибка компиляции «ожидается String, передано Int». До production вызов не доходит.
>
> ```scala
> def readBook(title: String): String = "Book: " + title
>
> readBook(123)
> // Ошибка компиляции
> ```
>
> Пример показывает: почему обратная связь приходит на этапе разработки, а не от пользователя.

##### Самодокументируемый код

Сигнатура показывает, что ожидается на входе и что вернётся, включая вариант отсутствия результата.

> [!example]- Пример: Плохо — обязательство в комментарии
> Тип результата обещает, что автор будет найден всегда. Оговорка про `null` живёт только в комментарии, компилятор её не читает.
>
> Ожидаемый результат: вызывающий код пишет `findAuthor(id).name` и падает с `NullPointerException`, когда автора нет.
>
> ```scala
> // может вернуть null, если автор не найден
> def findAuthor(id: AuthorId): Author = ???
> ```
>
> Пример показывает: для чего типы важнее комментариев — комментарий не обязывает вызывающий код ни к чему.

> [!example]- Пример: Хорошо — обязательство в типе
> `Option[Author]` означает «автор либо есть, либо нет». Обратиться к полю напрямую компилятор не даст.
>
> Ожидаемый результат: одна сигнатура передаёт то, что в других языках требует комментариев и соглашений.
>
> ```scala
> def findAuthor(id: AuthorId): Option[Author] = ???
> ```
>
> Пример показывает: почему сигнатура заменяет документацию — она не устаревает и проверяется компилятором.

##### Оптимизация и производительность

Статическая типовая информация позволяет компилятору:

- Избегать лишних проверок во время выполнения.
- Выбирать более эффективные инструкции JVM.
- Агрессивнее оптимизировать код.

Скомпилированный Scala-код сопоставим по производительности с Java, иногда превосходит его за счёт более точных типовых сведений.

##### Безопасность рефакторинга

При изменении типа компилятор становится списком задач: он перечисляет все места, которые перестали быть корректными.

> [!example]- Пример: Компилятор указывает места изменений
> Функция обращается к полю `title`. Если поле переименовать или изменить его тип, обращение перестанет компилироваться.
>
> Ожидаемый результат: после изменения `Book` компилятор перечислит все места, где код больше не согласован, — искать их вручную не нужно.
>
> ```scala
> def getBookTitle(book: Book): String = book.title
> ```
>
> Пример показывает: зачем строгие типы в большой кодовой базе — рефакторинг перестаёт быть рискованным.

## Механизмы усиления типовой безопасности

##### Вывод типов (Type Inference)

Вывод типов убирает шаблонные аннотации, не ослабляя строгость: тип всё равно фиксируется, просто его вычисляет компилятор.

> [!example]- Пример: Объявление без аннотаций
> Тип не написан ни у одного значения — компилятор берёт его из литерала справа.
>
> Ожидаемый результат: `pages` получает тип `Int` (целое число), `bookTitle` — `String` (строка); присвоить им значение другого типа не получится.
>
> ```scala
> val pages = 464              // выведен тип Int
> val bookTitle = "Clean Code" // выведен тип String
> ```
>
> Пример показывает: почему строгая типизация не означает многословность.

##### Параметрический полиморфизм (Generics)

Обобщённые типы позволяют написать одну реализацию для разных типов данных без приведения типов.

> [!example]- Пример: Обобщённая функция
> `T` — параметр типа: он подставляется при вызове. Компилятор гарантирует, что тип элемента списка и тип результата совпадут.
>
> Ожидаемый результат: для `List[Book]` функция вернёт `Book`, для `List[String]` — `String`; приведение типа не требуется.
>
> ```scala
> def first[T](list: List[T]): T = // T — заглушка для любого типа
>   list.head
>
> val books = List(
>   Book("Clean Code", 464, Author("Robert C. Martin")),
>   Book("Design Patterns", 395, Author("Erich Gamma"))
> )
>
> first(books) // тип результата — Book
> ```
>
> Пример показывает: для чего нужны generics — одна функция работает с любым типом и остаётся типобезопасной.

##### Null-безопасность через типы

Отсутствие значения моделируется явно, отдельным типом, а не значением `null`.

> [!example]- Пример: Плохо — отсутствие через null
> Отсутствие книги выражено значением `null`. Тип результата об этом не сообщает, проверку легко забыть.
>
> Ожидаемый результат: `findBook("Unknown").title` компилируется, но падает с `NullPointerException` при запуске.
>
> ```scala
> def findBook(title: String): Book =
>   if title == "Programming in Scala" then Book("Programming in Scala", 300, Author("Martin Odersky"))
>   else null // отсутствие спрятано от компилятора
>
> println(findBook("Unknown").title) // NullPointerException
> ```
>
> Пример показывает: почему `null` называют «ошибкой на миллиард долларов» — компилятор не помогает её предотвратить.

> [!example]- Пример: Хорошо — отсутствие через Option
> Тип `Option[Book]` означает «книга либо есть (`Some`), либо нет (`None`)». Достать значение можно, только разобрав оба случая.
>
> Ожидаемый результат: для `"Programming in Scala"` печатается название, иначе — `"Book not found"`. Пропустить ветку `None` компилятор не даст.
>
> ```scala
> def findBook(title: String): Option[Book] =
>   if title == "Programming in Scala" then Some(Book("Programming in Scala", 300, Author("Martin Odersky")))
>   else None
>
> findBook("Programming in Scala") match
>   case Some(book) => println(book.title)
>   case None       => println("Book not found")
> ```
>
> Пример показывает: зачем `Option` — обработка отсутствующего значения становится обязанностью, а не договорённостью.

## Философия типизации

##### Типы не позволяют выразить некорректное состояние

Если состояние невозможно корректно представить типами, оно не должно существовать.

> [!example]- Пример: Плохо — всё как String
> Автор описан обычной строкой. Компилятор одинаково примет имя автора, название книги и пустую строку.
>
> Ожидаемый результат: `Book("Dune", 412, "Dune")` компилируется, хотя в поле автора попало название книги.
>
> ```scala
> case class Book(title: String, pages: Int, author: String)
>
> Book("Dune", 412, "Dune") // ошибка не обнаружена
> ```
>
> Пример показывает: для чего нужны доменные типы — общий тип `String` не отличает одно понятие от другого.

> [!example]- Пример: Хорошо — отдельный тип на понятие
> Автор описан собственным типом. В поле `author` можно передать только `Author`.
>
> Ожидаемый результат: `Book("Dune", 412, "Dune")` — ошибка компиляции; корректный вызов — `Book("Dune", 412, Author("Herbert"))`.
>
> ```scala
> case class Author(name: String)
> case class Book(title: String, pages: Int, author: Author)
> ```
>
> Пример показывает: почему тип сильнее проверки в рантайме — некорректный вызов просто нельзя написать.

##### Типы выражают намерения разработчика

> [!example]- Пример: Сигнатура с бизнес-смыслом
> Имена и типы параметров описывают операцию предметной области: книга передаётся из библиотеки читателю.
>
> Ожидаемый результат: назначение функции понятно из сигнатуры, читать тело не требуется.
>
> ```scala
> def lendBook(from: Library, to: Reader, book: Book): Loan = ???
> ```
>
> Пример показывает: почему типы называют документацией — сигнатура описывает не технику, а бизнес-смысл.

##### Типы лучше комментариев

Комментарии устаревают и не проверяются компилятором.

> [!example]- Пример: Плохо — ограничение в комментарии
> Требование «страниц должно быть больше нуля» записано комментарием. Компилятор его не видит.
>
> Ожидаемый результат: `addBook("Dune", -5)` компилируется без замечаний.
>
> ```scala
> // pages must be positive
> def addBook(title: String, pages: Int): Book = ???
> ```
>
> Пример показывает: для чего ограничение выносят в тип — комментарий ничего не гарантирует.

> [!example]- Пример: Хорошо — ограничение в типе
> Отдельный тип `PositivePages` принимает только корректное значение, а функция требует именно его.
>
> Ожидаемый результат: передать `-5` напрямую нельзя — сначала нужно построить `PositivePages`, где и выполняется проверка.
>
> ```scala
> case class PositivePages(value: Int):
>   require(value > 0, "pages must be positive") // единственное место проверки
>
> def addBook(title: String, pages: PositivePages): Book = ???
> ```
>
> Пример показывает: почему типы надёжнее соглашений — их проверяет компилятор, а не дисциплина команды.
